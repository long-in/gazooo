# 47. ComfyUI の自動復旧(v0.47)

ステータス: 🟢 承認済み(2026-11-24。既定は OFF に変更して承認)。

## 1. 背景と目的

アプリが起動した ComfyUI が応答しなくなる(46 §13・§14)、またはプロセスが落ちると、生成のキューが止まり、利用者が手動で再起動するまで復旧しない。
**ComfyUI との接続が 90 秒以上続けて切れたら、アプリが ComfyUI を自動で再起動し、残っているキューを再起動後に実行し直す。** この機能は設定で ON/OFF できる。

## 2. 対象と前提

- 対象は **アプリが管理する ComfyUI**(15。`managed` で `enabled`)のみ。`external`(別途起動した ComfyUI)は、アプリが停止・起動できないため **対象外**(15 §5 と同じ。設定の項目も無効表示)。
- 利用者が [停止] を押して止めた場合(`stopped`)は **復旧しない**(意図した停止を覆さない)。対象の状態は `running`(プロセスは生きているが応答しない)と `crashed`(予期しない終了)。`starting` / `stopping` の間は何もしない。
- 15 §4 の「`crashed` は自動再起動しない」は、**この設定が ON のときに限り** 本書の復旧に置き換わる(OFF なら従来どおり)。

## 3. 設定

- `ManagedEngineConfig`(15 §3)に **`autoRecover: boolean`** を追加する。保存先は既存の `engine.comfyui.managed`(JSON)で、**DB のマイグレーションは不要**(欠けていれば既定値)。
- **既定は OFF**(Q-404。承認時に ON から変更)。利用者が設定で ON にしたときだけ働く。
- 画面: **設定 > ComfyUI の起動管理**(05 §設定)の「アプリ起動時に自動で起動」の下に、スイッチ「**応答しなくなったとき自動で再起動する**」を置く。説明文: 「ComfyUI との接続が 90 秒以上切れたら再起動し、残りのジョブを続けます」。`external` のときは無効(15 §9 の文言どおり)。日本語・英語。
- 90 秒のしきい値は **固定**(設定項目にしない。Q-405)。

## 4. 動作

### 4.1 検出

既存の接続監視(`services/engine.rs` の `monitor`。`/system_stats` の確認を一定間隔で行う)に、**切断の継続時間** を持たせる。

- 接続できた時点で継続時間を 0 に戻す。切れている間は、最初に切れた時刻 `disconnected_since` を保持する。
- `disconnected_since` から **90 秒以上** 経過し、§2 の条件を満たし、設定が ON なら、復旧を開始する。

### 4.2 再起動

- `EngineProcess::restart`(15 §5)と同じ処理(停止 → ポート解放待ち → 起動 → `running` まで待つ)を、**確認なしで**(`force`)呼ぶ。実行中のジョブは §4.3 で扱う。
- 成功の判定は 15 §4 の `running`(`/system_stats` が成功)。
- **試行の上限**: 切断が続く限り最大 **3 回**。失敗(`crashed`・起動タイムアウト)したら、次の試行は **再び 90 秒の切断が続いたあと**(間隔を空け、再起動の連打を防ぐ)。3 回失敗したら **あきらめ**、通知を出して、接続が一度回復するまで自動復旧を再開しない(Q-406)。
- ComfyUI の起動自体が失敗する原因(パス不正・ポート使用中)は、再試行しても直らないため、`ENGINE_PORT_IN_USE` / `ENGINE_LAUNCH_FAILED` は **1 回で打ち切る**。

### 4.3 キューの再実行

利用者の言う「キューが残っていれば再実行」を、次のとおりに定める。

1. **待機中のジョブ(`queued`)**: 切断中は **実行を保留**(ワーカーが次のジョブを取らない。一時停止と同じ扱いだが利用者の「一時停止」状態とは別)。再接続したら、順序どおりに続行する。保留しないと、待機中のジョブが次々に `ENGINE_UNREACHABLE` で失敗してしまう。
2. **実行中だったジョブ**: 切断で `ENGINE_UNREACHABLE`(または応答なしによる待機の失敗)になったとき、`autoRecover` が ON で `managed` なら、**失敗にせず `queued` の先頭に戻す**。再接続後に最初から実行し直す(生成は途中経過を引き継げないため、最初からやり直し)。
   - 同じジョブの自動再実行は **最大 2 回**(メモリ上で数える。アプリ再起動で 0 に戻る)。超えたら従来どおり `failed`(原因が接続ではなくジョブ自体の可能性。例: 46 §13 の特定の画像での停止)。
   - 利用者が取り消したジョブ・`ENGINE_UNREACHABLE` 以外の失敗は、再実行しない。
3. **あきらめたとき(§4.2)**: 保留を解除する。待機中のジョブは従来どおり実行を試み、`ENGINE_UNREACHABLE` で失敗する(消えずに履歴に残り、手動の [再試行] ができる)。
4. **アプリ起動時**に `running` のまま残っていたジョブは、従来どおり `failed`(02 §3.5)。本機能は **アプリの稼働中の復旧**だけを扱う。

> 実装時の確認事項: ComfyUI が固まったとき、ジョブの待機(`wait`)が `ENGINE_UNREACHABLE` で終わるか、待ち続けるか(46 §13 では HTTP が 10 秒でタイムアウト → 接続拒否)。待ち続ける場合は、再起動でプロセスが消えた時点で失敗するので、そこで §4.3-2 を適用する。違えば本書を更新して再承認を得る。

### 4.4 通知(UI)

イベント **`engine://recovery`**(04 に追記)を送り、画面に出す。

```ts
interface EngineRecoveryEvent {
  phase: "restarting" | "recovered" | "gave_up";
  attempt: number;          // 1〜3
  requeuedJobs?: number;    // recovered のとき、実行し直すジョブ数
}
```

- `restarting`: トースト「ComfyUI が 90 秒以上応答しないため、再起動しています」(サイドバーの接続バッジも「再起動中」)。
- `recovered`: トースト「ComfyUI を再起動しました。ジョブを続けます(N 件)」。
- `gave_up`: トースト(エラー)「ComfyUI を自動で再起動できませんでした。設定で状態とログを確認してください」。
- 再起動の事実は `tracing` の INFO ログにも残す(プロンプトは含めない)。

## 6. テスト

- **Rust(単体)**: `RecoveryTracker` — 89 秒では動かず 90 秒で動く / 接続回復で 0 に戻る / OFF・`external`・`stopped` では動かない / 3 回失敗であきらめ、回復後に再開する / 起動不能のエラーは 1 回で打ち切る。`ManagedEngineConfig` — `autoRecover` が欠けた既存 JSON が読め、既定が `false`。
- **Rust(ジョブ)**: 切断中は待機中のジョブが取り出されない / 実行中の `ENGINE_UNREACHABLE` は `queued` の先頭に戻る / 3 回目は `failed` / 取り消し・他のエラーは戻らない / あきらめで保留が解除される。
- **Vitest**: 設定のスイッチ(`external` で無効)、イベントによるトースト。
- **実機(09)**: ComfyUI のプロセスを一時停止(`Suspend-Process` 等)して 90 秒待つ → 再起動され、ジョブが続くこと。OFF では何も起きないこと。
