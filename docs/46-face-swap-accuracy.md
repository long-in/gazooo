## 3. A. 複数候補の生成と選択

- 画面に **「候補の数」**(1〜4。既定 1)を追加する。2 以上のとき、対象画像 1 枚につき **シードだけ違うジョブを N 件** 投入する(42 §4.3 と同じく、フロントが `job_enqueue` を繰り返す。バックエンドの仕組みは増やさない)。
- 生成した候補は、ギャラリーで **同じ対象から作ったもの** として並べて見られるようにする(既存のギャラリーの並び・複数選択を使う。新しい比較画面は作らない)。気に入らない候補は、既存の複数選択で削除できる。
- 所要時間は N 倍になる(8 ステップで約 90 秒 × N)。画面に目安を表示する(「3 枚 × 候補 2 = 約 9 分」)。
- スキーマ変更なし。`faceSwap` には `candidates` を **保存しない**(投入時だけのフォームの状態。42 §14 の「対象画像の一覧」と同じ扱い)。

## 4. C. 入れ替え後の顔の再描画(ディテール補正)

**目的**: 8 ステップで甘くなる目・肌を、顔の領域だけ **低 denoise で再サンプリング** して回復する。

**課題**: 10 の `FaceDetailer` は SD 1.5 / SDXL 向けの設計(§4.2・§5 の `sd15` / `sdxl` のみ)。Qwen-Image 2.1 は参照画像を `TextEncodeQwenImage21` で条件に入れる構成で、`FaceDetailer` の再サンプリングにそのまま通るか分からない。

### 4.1 案

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| C1 | Impact Pack の `FaceDetailer` を Qwen-Image 2.1 のモデル・条件で動かす | 既存の仕組み(10)・ノードが導入済み | 動くか未確認。参照画像つきの条件で顔が崩れる恐れ |
| C2 | 検出した顔(頭)の領域を切り出し、Qwen-Image 2.1 で **低 denoise の img2img** にかけて貼り戻す(合成のマスク 42 §5 を流用) | 既存のマスク・検出器を流用できる | Qwen-Image 2.1 の img2img がアプリに未実装(要・確認) |
| C3 | 顔復元モデル(CodeFormer / GFPGAN 系)で顔領域を復元して貼り戻す | 軽い。顔が崩れにくい | 追加ノード・モデルの導入が必要。肌がなめらかになりすぎる |

**推奨**: **C1 を実機で試し、通らなければ C3**。C2 は img2img の実装が別に要るので、本変更では扱わない。結果は §7 の確認項目で確定してから、本資料の §4 を更新する。

### 4.2 パラメータ(案。C1・C3 のどちらでも共通)

```ts
interface FaceSwapParams {
  // ... 42 §4.1
  refine?: { enabled: boolean; denoise: number }; // 顔の再描画。既定 { false, 0.3 }
}
```

- 既定は **OFF**(時間が伸びるため)。ON のとき、後段合成(`keepOutside`)の **前** に顔の領域だけ再描画し、その結果を合成する。
- `denoise` の範囲は 0.1〜0.5(大きいほど顔が変わり、似方が崩れやすい)。
- 排他は 42 §4.2 のまま(`faceDetailer` との同時指定は不可。再描画は `faceSwap.refine` が担う)。

## 5. B. 合成マスクの改善

42 §5.1 の手順 2 を次のとおり強める。

1. **輪郭のぼかしを標準にする**: `ImpactGaussianBlurMask` を `head` / `face` の両方に適用する(`face` はぼかし付きの見た目が **未確認**。§7)。
2. **髪の切れ対策**: `head` のマスクを **下方向へ非対称に広げる**(検出領域の下側を、上側の約 1.5 倍)。顔画像の髪が長いときの切れ方を減らす。
3. **楕円化**: 長方形のままにせず、`face` では検出領域に内接する楕円に近づける(実現方法は §7 の確認。ノードで難しければ、ぼかしの強化で代える)。
4. 範囲の値(`GrowMask` の px、`crop_factor`、ぼかしの `kernel_size` / `sigma`)は、実機の目視で確定する。

画面の操作は増やさない(`region` の 2 択のまま)。値の調整は内部の固定値で行う。

## 6. D・E・F

### D. 顔画像のガイドと品質チェック

- 顔画像の選択時に、**短辺 < 512 px** のとき警告を出す(「小さい顔画像は似方が弱くなります」)。生成は止めない。
- 画面に、顔画像の選び方の短い案内を置く(正面寄り・髪型が対象に近い・加工や強い影が無い)。
- 画像の寸法は、取り込み時(`input_image_pick`)に Rust が返している情報で足りる(**新しい IPC は不要**の想定。実装で確認)。

### E. 顔が検出できなかったときの扱い

42 §14 は「入れ替わらない画像が成功として出る」。これを、**検出が空なら、そのジョブを失敗(`FACE_NOT_DETECTED`)にして知らせる**よう改める。
- **生成の前に確認する(2026-11-24 の設計変更。§13)**: 顔のない画像を対象にすると、実機で Qwen-Image 2.1 + LoRA の生成が止まり、ComfyUI ごと応答しなくなった(4 回中 4 回)。生成のあとで判定する方式では間に合わないため、`keepOutside` が有効のとき、**重い生成の前に、顔の有無だけを調べる軽いワークフロー**(`LoadImage` → 検出 → `ImpactCount_Elts_in_SEGS` → `PreviewAny`。モデル不要で数秒)を実行し、0 件なら生成を始めずに失敗にする。
- 生成のあとの判定(§13 の `PreviewAny` の数)も、念のため残す。
- 検出の有無は、数を `PreviewAny` で履歴へ出して読む(実機で確認済み。§13)。
- 失敗にしても、`keepOutside` を切って再生成できる旨を画面で案内する。
- エラーコードの追加は 04 に反映(承認後)。

### F. LoRA の版の選択

- 42 §7 の他の 2 版(`v1.1_alternative`、`v1`)を、設定の「詳細」から選べるようにする。強さは 1.0 のまま。
- カタログへ 2 件追加する(サイズ・SHA-256 は取得後に実測して確定)。
- 優先度は低い。A〜E で足りなければ着手する。

## 13. 実装時の判断(設計との差異・補足。2026-11-24)

実装済み: **A・B・D**。Rust 11 テスト(顔の入れ替え)・Vitest(生成 100 件)・tsc・ESLint・`cargo fmt --check`・`cargo clippy -D warnings` まで確認。

**実機確認(2026-11-24。RTX 2060 12GB・ComfyUI 0.45.6。合成した人物画像: 対象 = 公園の男性、顔 = 赤く長い髪の女性。8 ステップ)**: 後段合成の `head`(下方向 60 px 拡張あり)は、`MaskComposite` を含めて **バリデータに受理され、生成に成功した(135 秒。モデルの読み込みを含む)**。出力は元と同じ 768×1024。目視で、頭が自然に入れ替わり、**長い髪が胸の高さまで流れても途中で切れず、継ぎ目も見えなかった**。頭以外は元画像のまま。60 px の効果を拡張なしと並べた比較・複数人・横顔・小さな顔は **未実施**(§7-3・5 は残る)。

- **A は新しい「候補の数」を作らない(§3 との差異)**: 生成ボタンの横に **既存の「投入回数」(`count`)** があり、顔の入れ替えでも「対象の枚数 × 回数」のジョブが投入され、各ジョブはシードが変わる。これで足りるので、項目は増やさず、顔の入れ替えセクションに **「N 枚 × M 回 = 約 X 分」の目安**(1 ジョブ = ステップ数 × 11.5 秒。8 ステップ約 92 秒・25 ステップ約 288 秒。実測 42 §9.1 から)と、候補の使い方の一文を足した。
- **B は「頭」の下方向への拡張だけ**: 検出マスクを 60 px 下へずらした複製との和集合(コアノード `MaskComposite`、`or`。ノード ID 120)にしてから `GrowMask` へ渡す。`face` は変えない。楕円化・`face` のぼかしの検証(§7-3)は未実施のため入れていない。`faceSwapComposite` の必須ノードに `MaskComposite` を加えた(9 → 10)。**60 px は仮の値**で、実機の目視で調整する(固定値。画像の大きさに比例させてはいない)。
- **E は実装済み・実機確認済み(2026-11-24)**: **生成の前に顔の有無を確認する方式**(§6 E)にした。`submit_prompt` が、顔の入れ替え + 後段合成のとき、モデル不要の軽いワークフロー(`LoadImage` → `BboxDetectorSEGS` → `ImpactCount_Elts_in_SEGS` → `PreviewAny`。ノード ID 1〜5、出力 4)を先に投入して履歴の数を読み、0 件なら `FACE_NOT_DETECTED` で失敗にする(生成は投入しない)。**実機: 顔なしの 2 枚(単色の背景、写真から切り出した脚と地面)は約 0.6 秒で `FACE_NOT_DETECTED`、顔のある画像は従来どおり 123 秒で生成に成功**。Rust 492 件(事前確認の有無・生成を投入しないことの検証を含む)・clippy・fmt が通過。以下の「生成のあとの判定」は、事前確認をすり抜けた場合の保険として残してある。
- **ComfyUI の停止の再調査(同日)**: 上の経緯の停止は、アプリが起動した ComfyUI で 4 回起きた。**ComfyUI を直接起動し、ログをファイルへ出す形に替えたところ、顔のない画像(事前確認なしの旧コード)でも 117 秒で最後まで通り、HTTP も止まらなかった**(`Prompt executed in 116.90 seconds`)。このため、停止の原因は「顔のない画像」より **アプリ経由の起動(出力のパイプ)側** の可能性が出てきた(42 §12 の「ComfyUI を直接起動した再実行では再現しなかった」と同じ)。**原因は未特定**で、顔のない画像との因果は確定していない。事前確認は、停止の有無にかかわらず、無駄な生成(約 2 分)を避ける意味がある。
- **ComfyUI の停止の原因調査(2026-11-24。原因は未特定)**。症状: HTTP が応答せず、プロセスは生存、GPU・CPU はほぼ遊び、VRAM は約 11GB を保持。アプリのログでは、止まる前にヘルスチェック(`/system_stats`)の応答が生成中に遅くなり(4.2 秒・0.6 秒)、直後から 10 秒でタイムアウトし、のちに接続拒否になる(5 回とも同じ形)。止まったのはすべて **アプリが起動した ComfyUI を、別プロセス(実機テスト)から使ったとき**で、同じ日の 11 時台にアプリ自身が実行した顔の入れ替え 4 件(各約 112 秒)は問題なく完了している。**否定できたもの**(いずれも顔なしの画像・合成なしで 117〜131 秒で完了し、止まらなかった): ① 直接起動(ログをファイルへ)、② `/system_stats` を 2 秒ごとに生成中ずっと呼ぶ(最大 2.4 秒の遅れは出るが回復)、③ アプリと同じ起動経路(`EngineProcess`。出力のパイプ・Job Object・コンソールなし)、④ ③ にアプリと同じ `health()`(`/system_stats` + ノード定義の問い合わせ 約 20 件)を 5 秒ごとに加える。出力のパイプの読み取り(`read_lines`)も、常に読み続ける作りで、詰まる経路は見当たらない。**残る候補**: アプリ本体(GUI)が動いていること。具体的には、(a) WebView2 / デスクトップの GPU 使用で、12GB の VRAM が足りなくなり(ComfyUI が約 11GB を使う)、ドライバが共有メモリへ逃がして CUDA が固まる、(b) ログ(`engine://log`)のイベントでフロントが詰まる、のどちらか。アプリを起動した状態での再現が必要で、再現用に `real_comfyui_face_swap_through_the_app_launcher`(`#[ignore]`。`NO_HEALTH=1` でヘルスチェックを切れる)を足した。

## 14. ComfyUI の停止への対策(2026-11-24。承認済み・実装済み)

### 14.1 問題と根拠

アプリが起動した ComfyUI が、同じプロセスで生成を繰り返すうちに HTTP に応答しなくなる(§13)。**動的 VRAM ロード(ComfyUI 0.45 の既定)が有効だと 3 回目で停止し、`--disable-dynamic-vram` では 4 回連続で完了した**(110 秒台。速度の低下なし)。顔の入れ替え(Qwen-Image 2.1 + LoRA)に限らず、VRAM が 12GB 級で大きなモデルを繰り返し読み込む構成で起こりうる。

### 14.2 提案: 起動引数に `--disable-dynamic-vram` を加える

- アプリが ComfyUI を起動するとき(`LaunchSpec`。15 §6)、**ComfyUI がこの引数に対応している場合だけ** `--disable-dynamic-vram` を付ける。
  - 対応の判定: `main.py` と同じ場所の `comfy/cli_args.py` に `--disable-dynamic-vram` の文字列があるか(ファイルを読むだけ。プロセスは起動しない)。読めない・見つからないときは付けない(古い版は未知の引数で起動に失敗するため)。
  - 固定の引数であり、**任意の追加引数は受け付けない**方針(15 §6・§8)は変えない。
- **全 OS で同じ扱い**。macOS(Apple Silicon)は既定で動的 VRAM が無効なので、引数があっても動作は変わらない。
- 設定項目は **設けない**(常に無効)。止まる不具合を避けるのが目的で、速度の低下が見られないため。必要になったら設定へ出す(Q-397)。
- 開発用の `tools/comfyui/start.ps1` / `start.sh` にも同じ引数を加える(08)。
- アプリの外で起動した ComfyUI(`managed` でない接続)は対象外。ユーザーが自分の起動引数で決める。

### 14.3 補足の対策(別変更。本案には含めない)

- **応答しなくなったことの検出と案内**: 生成中のヘルスチェックが連続で失敗したとき、「ComfyUI が応答しません。再起動しますか?」を出す(42 §12 の無応答の扱い)。現状は 10 秒のタイムアウトのあと接続拒否まで、原因が分かりにくい。
- 数回の生成ごとの自動再起動は、**行わない**(再起動で数十秒かかり、生成のキューが止まるため。引数で解消すれば不要)。
