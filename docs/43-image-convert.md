# 43. 画像の形式変換(複数画像を一括で PNG / JPEG / WebP に変換、v0.38)

> ステータス: 🟢 承認済み(2026-11-23。07 Q-349〜366 は推奨どおり。Q-357 は `webp` クレートを追加する)。実装済み(Rust 481・Vitest 372・clippy・ESLint・静的エクスポートのビルドまで確認。**画面の目視確認・ドロップの実機確認・macOS は未実施**。差異は §12)。
> **経緯**: 「画像を別の形式へ変換する機能がほしい。専用のページを設け、アプリへドラッグ&ドロップして複数でも一括変換したい。変換前の形式は自動判断し、指定の形式へ変換する。変換時のクオリティを指定でき、変換後のファイルを置くフォルダも指定する。**取り込む形式では WebP に絶対に対応する**」という要望(2026-11-23)。直前に「WebP を参照画像に登録できない」という指摘もあった(§9)。

## 1. 目的とスコープ

**やること(F-22)**
- 専用ページ `/convert`(ナビに「変換」を追加)で、画像ファイルを **一括で別の形式へ変換**する。
- 入力: ファイルのドラッグ&ドロップ(複数・フォルダも可)、または [ファイルを選択]・[フォルダを選択]。
- **入力形式は拡張子ではなく中身で自動判断**する(§3)。**WebP は必須対応**(静止画の lossy / lossless / アルファ付き)。
- 出力形式(PNG / JPEG / WebP)と **品質** を指定できる(§4)。
- **出力先フォルダを指定**する(必須。前回の値を記憶)(§5)。
- 参照画像の取り込みでも WebP を受け付ける(§9)。

**やらないこと(v0.38)**
- 元ファイルの変更・削除・上書き(出力先へ **新しいファイルを書くだけ**)。
- リサイズ・トリミング・回転・色調補正などの編集。
- 動画・アニメーション(アニメ GIF / アニメ WebP は **先頭 1 フレームだけ** を変換し、結果の一覧に注記する)。
- ギャラリー・DB・ComfyUI との連携(変換結果はギャラリーに登録しない。ComfyUI 未起動でも使える)。
- メタデータ(EXIF・ComfyUI のプロンプト埋め込み等)の引き継ぎ(§4.4)。

## 2. 画面(`/convert`)

```
┌ 変換 ───────────────────────────────────────────────┐
│ ┌ ここにファイル / フォルダをドロップ ─────────────┐ │
│ │      [ファイルを選択]  [フォルダを選択]          │ │
│ └─────────────────────────────────────────────────┘ │
│ 変換する画像 (12)                    [すべて外す]    │
│  ▢ a.webp   WebP  1920×1080  412KB   [×]            │
│  ▢ b.png    PNG   1024×1024  1.2MB   [×]            │
│  ▢ x.txt    ⚠ 画像として読めません(変換から除外)    │
│ ─────────────────────────────────────────────────── │
│ 出力形式  (PNG) (JPEG) (WebP)                        │
│ 品質      ──●───── 85   ☐ ロスレス(WebP のとき)     │
│ 背景色    ■ 白   (透明を JPEG にするとき)            │
│ 出力先    C:\Users\...\Pictures\converted  [変更]    │
│ ☐ 出力先に元と同名がある場合は上書き(既定: 連番)    │
│                                  [12 枚を変換]       │
│ 進捗 ████████░░ 8/12  [中止]                         │
│ 結果: 成功 11 / 失敗 1 ・ 合計 38.2MB → 9.1MB  [フォルダを開く] │
└─────────────────────────────────────────────────────┘
```

- ドロップ領域は **ページ全体**でも受け付ける(`/convert` を開いているときのみ)。他のページにドロップしても何も起きない。
- 一覧は仮想化しない(上限 1000 枚。§3.3)。各行に、検出した形式・画素数・サイズ・失敗理由を出す。個別に外せる。
- 出力形式に応じて項目を出し分ける(§4.1)。変換中は設定・一覧を操作不可にし、[中止] だけ有効にする。
- 完了後、結果の一覧(成功 / 失敗・出力ファイル名・サイズの前後)と [出力フォルダを開く]。

## 3. 取り込み(入力)

### 3.1 対応する入力形式と自動判断

| 形式 | 対応 | 備考 |
|---|---|---|
| **WebP** | **必須** | lossy / lossless / アルファ付きの静止画。アニメ WebP は先頭フレームのみ |
| PNG | ◯ | 16bit・アルファ・パレットを含む |
| JPEG | ◯ | EXIF の向きを反映してから変換する |
| GIF | ◯ | 先頭フレームのみ |
| BMP | ◯ | |
| TIFF | ◯ | 一般的な圧縮のみ(`image` クレートが対応する範囲) |

- **形式の判定は先頭バイト(マジックナンバー)で行う**(`image::guess_format` 相当)。拡張子は参考にしない(`.jpg` という名前の WebP も正しく読む)。判定できない・デコードできないファイルは **その行だけ失敗**として理由を表示し、ほかの変換は続ける。
- 対応外の形式(HEIC・AVIF・RAW・SVG・PSD 等)は「対応していない形式です」と表示する(将来の拡張)。

### 3.2 取り込み経路(WebView にパスを渡させない)

AGENTS.md の方針(パスをフロントから受け取らない。WebView から任意ファイルを読ませない)を守る。

- **ドロップ**: Tauri のウィンドウのドラッグ&ドロップイベントを **Rust 側** で受け(`WindowEvent::DragDrop`)、パスを `ConvertService` の一時リスト(セッションごと・メモリのみ)に登録し、`convert://added` で「`id`・ファイル名・検出形式・画素数・サイズ・エラー」だけをフロントへ通知する。フロントは以降 `id` で指す。
- **ダイアログ**: [ファイルを選択]・[フォルダを選択] は Rust 側でダイアログを開く(`input_image_pick_many` と同じ方式)。
- `tauri.conf.json` の `dragDropEnabled` が有効であることを実装時に確認する(無効だと WebView の HTML5 ドロップになり、パスが取れない。Windows の既定は有効)。
- フロントが渡すのは `id` の配列と変換設定だけ。任意のパスで変換させる経路は作らない。

### 3.3 フォルダと上限

- フォルダは **再帰的に展開**し、対応形式(§3.1)と判定できたファイルだけを一覧に加える(隠しフォルダ・シンボリックリンクの先は辿らない)。
- 一覧は最大 **1000 枚**。超えた分は無視し、通知する。同じパスの重複登録は 1 つにまとめる。
- 1 枚あたりの上限: **1 億画素**(デコード前に寸法を読んで判定し、超えるものはメモリ枯渇を避けるため失敗扱い)。

## 4. 変換(出力)

### 4.1 出力形式と品質

| 出力 | 品質の意味 | 設定 |
|---|---|---|
| **PNG** | ロスレス(品質の指定なし。スライダーは無効化) | 圧縮レベル(速い / 標準 / 小さい。既定 標準)。ファイルサイズだけが変わる |
| **JPEG** | 1〜100(既定 90) | アルファは背景色に合成(§4.2) |
| **WebP** | 0〜100(既定 85)の lossy | **[ロスレス] スイッチ**で可逆圧縮(品質は無視) |

- 品質スライダーの横に「大きいほど高画質・ファイルが大きい」と説明を出す。
- 設定(形式・品質・ロスレス・背景色・出力先・上書き)は **設定ストアに保存**し、次回も復元する(ユーザーごと。36)。

### 4.2 透明(アルファ)の扱い

- PNG / WebP へ: アルファを保持する。
- JPEG へ: アルファを **背景色に合成**してから変換する(既定 白。色は選択可)。
- 入力にアルファが無ければ、何もしない。

### 4.3 色・向き・ビット深度

- JPEG の EXIF の向き(Orientation)は、**ピクセルへ反映してから**書き出す(向きの情報は出力に残さない)。
- 16bit 入力は、8bit 出力の形式(JPEG・WebP)では 8bit に落とす。PNG へは 8bit で出す(16bit の維持は対象外)。
- ICC プロファイルの変換はしない(sRGB 前提。引き継ぎもしない)。

### 4.4 メタデータ

**引き継がない**(出力に EXIF・テキストチャンク・ICC を含めない)。ComfyUI が PNG に埋め込むプロンプト・ワークフローも消える旨を、画面に 1 行注記する(プライバシー目的でも使える)。

## 5. 出力先と名前

- **出力先は必須**。未指定のときは [変換] ボタンを無効にして理由を示す。ダイアログは Rust 側で開き、選んだパスは Rust 側で検証して保存する(存在・書き込み可能)。
- **既定の出力先**: 初回は OS の「ピクチャ」フォルダ配下の `gazooo-converted`(無ければ変換時に作成)。2 回目以降は前回の値。
- 出力ファイル名: `<元のファイル名の拡張子を除いた部分>.<新しい拡張子>`(`png` / `jpg` / `webp`)。
- **既定は上書きしない**。同名がある場合は ` (1)`・` (2)` … の連番を付ける。[上書き] を選んだときだけ置き換える(元ファイル自身を出力先が指す場合は、上書き設定でも連番にする = **元ファイルは決して壊さない**)。
- フォルダを取り込んだ場合も、出力は **出力先の直下へフラットに**書く(相対パスの再現はしない)。同名は連番で衝突を避ける。
- 使えない文字・長すぎる名前は、Windows の制約に合わせて置換・切り詰める(OS 依存コードは `std::path` で扱う。06)。
- 書き込みは一時ファイル → 名前変更の順に行い、失敗・中止で途中のファイルを残さない。

## 6. 実行と進捗

- Rust 側の `ConvertService`。デコード・エンコードは CPU 処理なので `spawn_blocking`(または専用スレッド)で並列に実行する(同時実行数 = 論理 CPU 数の半分、最大 4。メモリを使う画像が重ならないように)。
- 進捗は `convert://progress`(`{ done, total, current? }`)と、1 枚ごとの結果 `convert://item`(`{ id, ok, outputName?, inBytes, outBytes?, error? }`)で通知する。
- [中止]: 実行中の画像は完了させ、**未着手の画像は処理しない**(出力済みのファイルは残す)。
- 1 枚の失敗で全体を止めない。最後に成功・失敗の件数を出す。
- 一時ファイルは名前変更のため出力先と同じフォルダに `*.gazooo-tmp` で作る。変換中にアプリが終了すると残る場合があるが、無害なので掃除はしない(起動時に出力先を走査しない)。

## 7. 実装方針(技術)

- 依存(固定バージョン。AGENTS.md「依存バージョンの固定」)。
  - `image`(既存 `=0.25.10`)に feature **`webp`・`gif`・`bmp`・`tiff`** を追加する(デコード)。`image` の WebP は純 Rust(`image-webp`)で、**デコードは lossy / lossless とも対応、エンコードはロスレスのみ**。
  - **lossy WebP の書き出し**には libwebp が必要なため、**`webp` クレート(`libwebp-sys`。C のソースを同梱してビルド)を 1 つ追加する案**(Q-357)。`rusqlite`(bundled)で C コンパイラは既に必要なため、ビルド要件は増えない。ライセンスは非商用前提のため選定基準にしない。
  - JPEG の品質指定は `image::codecs::jpeg::JpegEncoder::new_with_quality`、PNG の圧縮レベルは `PngEncoder::new_with_quality`。
- 配置: `src-tauri/src/services/convert.rs`(変換処理。純粋関数として単体テスト可能にする)、`src-tauri/src/commands/convert.rs`、ドロップのイベント受けは `lib.rs` の `on_window_event`。フロントは `src/app/convert/page.tsx`・`src/lib/tauri/convert.ts`(薄いラッパー)・`src/components/convert/`。
- 検証・テスト:
  - Rust: 形式判定(拡張子と中身が違う例)、WebP(lossy・lossless・アルファ)の入出力、JPEG のアルファ合成、EXIF の向き、連番の衝突回避、元ファイルを上書きしないこと、上限(画素数・枚数)、中止。テスト用画像はコード内で生成する。
  - フロント: 出力形式ごとの項目の出し分け、出力先未指定での無効化、設定の復元(Vitest)。

## 8. データ・IPC・設定

- **DB のスキーマ変更なし**(マイグレーション不要)。変換結果は保存しない。
- 設定ストアに追加するキー: `convert.format`(`png` | `jpeg` | `webp`)、`convert.quality`(1〜100)、`convert.webpLossless`、`convert.pngCompression`、`convert.background`(`#rrggbb`)、`convert.outputDir`、`convert.overwrite`。
- IPC(04 に追記。型は 04 が正):
  - `convert_pick_files()` / `convert_pick_folder()` → `ConvertEntry[]`(ダイアログは Rust 側)
  - `convert_pick_output_dir()` → `{ path } | null`
  - `convert_remove({ ids })` / `convert_clear()`
  - `convert_run({ ids, format, quality, webpLossless, pngCompression, background, overwrite })` → `{ runId }`(出力先は保存済みの値を使う)
  - `convert_cancel({ runId })`
  - `convert_open_output_dir()`(出力先を OS のファイラーで開く)
  - `ConvertEntry = { id, name, detectedFormat, width, height, bytes, error? }`
  - イベント: `convert://added`・`convert://progress`・`convert://item`・`convert://finished`(`{ ok, failed, inBytes, outBytes, cancelled }`)
  - エラー: 出力先が未設定・書き込み不可は `VALIDATION`(`details.field = "outputDir"`)、`id` 不明は `NOT_FOUND`。
- capability: ダイアログは既存の `dialog` を使う。ファイルの読み書きは Rust 側で行い、WebView に fs 権限は与えない。

## 9. 参照画像の WebP 対応(ご指摘の件)

現状は PNG / JPEG のみ(ダイアログのフィルタ `png`・`jpg`・`jpeg`、`image` クレートの feature `png`・`jpeg`)。次のとおり WebP を足す。

- `image` の feature に `webp` を追加(§7 と同じ)。
- `input_image_pick`・`input_image_pick_many` のフィルタに `webp` を追加。
- 取り込み(`InputService::import_file`)は、**形式を中身で判定してデコードし、`inputs/<uuid>.png` へ保存**する(既存の保存形式は変えない。Qwen・ControlNet・Inpaint などの下流は PNG のまま)。アニメ WebP は先頭フレーム。
- ギャラリー・貼り付け等、ほかの入力経路が見つかれば同様に対応する(実装時に洗い出す)。
- `docs/24` ほか「PNG / JPEG」と書かれた箇所の文言を「PNG / JPEG / WebP」へ更新する(実装時に差分を確認して同期)。

## 10. 他機能との関係・注意

- 生成・キュー・ComfyUI の状態に依存しない。生成中でも使える(CPU を使うため、生成中は同時実行数を下げるかは Q-364)。
- ユーザー機能(36): 設定は各ユーザーのストアに保存。変換結果はユーザーのデータ領域の外(ユーザー指定のフォルダ)に出る。
- AI サポート(11)の機能カタログに「画像の形式変換ページ」の案内を 1 行追加する(実装時)。
- バックアップ(35)の対象外(DB・画像を持たない。設定値のみ)。

## 12. 実装時の差異・補足

- **画面のショートカット**: ナビに「変換」を設定の前へ加えたため、`Ctrl/⌘ + 5` が変換、`Ctrl/⌘ + 6` が設定になった(従来の 5 = 設定から 1 つずれる)。
- **ドロップの受付**: ページを開いている間だけ受け付けるため、`convert_set_accepting` と、ドラッグ中の強調用イベント `convert://drag` を追加した。一覧の復元用に `convert_list` も追加した(04 の追記に準じる)。
- **取り込み時の検査**: 先頭を読んだだけで壊れていると分かるファイルは、取り込みの時点でエラー行になり、変換の対象から外れる(§2 の一覧の表示どおり)。変換中に起きた失敗(取り込み後にファイルが消えた等)は、その 1 枚だけが失敗する。
- **設定の保存**: `convert.settings` の 1 つのキー(ユーザーごと)に JSON で保存する。出力先は専用のダイアログ(`convert_pick_output_dir`)で選んだときだけ保存し、未設定の間は `ピクチャ/gazooo-converted` を使う。
- **EXIF の向き**: デコード時に画素へ反映する(`image` の `orientation`)。
- **未確認**: 実機でのファイルのドロップ(Windows)、アニメ WebP の先頭フレームの変換、macOS。

## 13. 追補: HEIC / HEIF の入力対応(v0.48、🟢 承認済み(2026-11-24)・実装済み。差異は §13.6)

> **経緯**: 「画像変換機能において、入力に HEIC に対応したい」(2026-11-24)。§3.1 で「将来の拡張」とした HEIC を入力に加える。iPhone の写真の標準形式を、PNG / JPEG / WebP へ変換できるようにするのが目的。

### 13.1 スコープ

- 入力形式に **HEIC / HEIF**(拡張子 `.heic`・`.heif`・`.hif`。中身は ISO BMFF の `ftyp` ボックスのブランド `heic`・`heix`・`mif1`・`msf1` 等)を追加する。判定は §3.1 と同じく **中身(先頭バイト)** で行う。
- 出力形式・品質・出力先・連番・メタデータ(引き継がない)の扱いは §4〜6 のまま。
- HEIC 内の **向き(`irot`・`imir`)** はピクセルへ反映してから書き出す(§4.3 と同じ方針)。アルファ付き HEIC は §4.2 に従う。
- 複数画像を含む HEIC(バースト・Live Photo の静止画部)は **プライマリ画像 1 枚** だけを変換する(アニメ GIF と同じ注記を結果に出す)。深度マップ・補助画像は無視する。
- 10bit の HEIC(HDR)は 8bit に落とす(§4.3 の 16bit と同じ。トーンマッピングはしない。色が変わる旨を注記)。
- **AVIF は対象外**(同じ ISO BMFF だが別のデコーダが必要。要望があれば別途)。
- 参照画像の取り込み(§9。`input_image_pick*`)へ HEIC を広げるかは Q-414。

### 13.2 デコード方式(Q-411。**段階 A の確認の結果、案 C を採用**。§13.6)

`image` クレートは HEIC をデコードできない。次のいずれかで足す。当初の推奨は A(libheif を静的に同梱)で、段階 A で確認してから確定する方針だった。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|

### 13.3 変更点(実装時の差分)

- `services/convert.rs` の形式判定に HEIC を追加(`image::guess_format` で判定できないため、`ftyp` ブランドを自前で見る小さな関数)。デコードは §13.2 の方式へ分岐し、得た `DynamicImage` 以降は既存のエンコード処理をそのまま使う(WebP と同じ経路)。
- `ConvertEntry.detectedFormat` に `"heic"` を追加(04 の型を更新)。画面の形式バッジは「HEIC」。
- ダイアログの拡張子フィルタ([ファイルを選択])に `heic`・`heif` を追加。フォルダの再帰展開(§3.3)でも HEIC を対象に含める。
- 対応外の形式のメッセージ(§3.1 末尾)から HEIC を外す(AVIF・RAW・SVG・PSD は残す)。
- DB・設定キーの変更なし。IPC のコマンド・イベントの追加なし(`detectedFormat` の値が増えるだけ)。
- テスト: HEIC のテスト画像(数 KB の小さなファイルを `src-tauri/tests/fixtures/` に置く。著作権の問題がない自作 or 生成したもの)の判定・デコード・向き・各形式への出力、壊れた HEIC が 1 行の失敗になること。HEIC の **エンコード** はしない(テスト画像は外部ツールで作って同梱)。
- 09 に実機確認を追加: iPhone の HEIC(縦向き・10bit・Live Photo)を変換し、向きと色が正しいこと。

### 13.6 実装時の差異・補足(段階 A の結果)

- **デコード方式は案 C(純 Rust の `zune-heic =0.5.0`。MIT / Apache-2.0 / Zlib)に確定**。理由: 開発機(Windows)に CMake・C++ の準備がなく、案 A はビルド要件が増える。一方 `zune-heic` は実機の iPhone の HEIC(3024×4032・縦向き・ICC 付き)で、向き・色とも正しくデコードできた(1 枚約 150〜200ms)。依存の追加は `Cargo.toml` の 1 行のみで、C/C++ のビルド要件は増えず、06 の変更も不要。
- 配置: `services/heic.rs`(判定 `is_heic`・寸法 `dimensions`・デコード `decode`)。変換ページ(`services/convert.rs`)と参照画像の取り込み(`services/inputs.rs`)が共通で使う。デコードのパニックは 1 枚の失敗として扱う(`catch_unwind`)。
- **Q-412〜414 は推奨どおり**。10bit は 8bit にデコードされる(トーンマッピングなし)。注記の表示は未実装(結果への注記は今後)。参照画像の取り込み(ダイアログのフィルタ `heic`・`heif`、PNG へ保存)にも HEIC を足した。参照画像の長辺の上限(8192px)は従来どおり。
- **テスト**: HEIC の小さなテスト画像は同梱していない(エンコーダが無く、手元の実写真は個人情報を含むためリポジトリに入れない)。代わりに、ブランド判定・壊れた HEIC の失敗は単体テスト、実ファイルでの判定・デコード・3 形式への出力は `GAZOOO_HEIC_SAMPLE=<path> cargo test --release heic_real -- --ignored`(`#[ignore]`)で確認した。
- **未確認**: 画面の目視、ドロップの実機確認、10bit(HDR)・Live Photo・バースト・アルファ付きの実ファイル、macOS。
