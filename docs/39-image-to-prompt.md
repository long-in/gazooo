# 39. 画像からプロンプトを作る(タガー、F-20、v0.34)

> ステータス: 🟢 承認済み・実装済み(2026-11-22。Q-287〜300 は推奨どおり確定。07 B36)。Rust 445・Vitest 302・clippy・ESLint・静的エクスポートのビルドまで確認。実機の ComfyUI + WD14 Tagger での動作確認は 2026-11-22 に Windows で実施済み(§13.3)。**画面の目視確認・macOS は未実施**(差異は §13)。
> 経緯: 「画像を取り込んでプロンプトを出力できないか」という要望。19(img2img)では Q-86 で「元画像からのプロンプト自動生成は行わない(ローカルのタガーは別設計)」としていた。ユーザーの選択により、**ComfyUI のカスタムノード(WD14 Tagger)を使う方式(案 B)** で設計する。画像は外部へ送らない(ローカルの ComfyUI のみ)。

## 1. 目的とスコープ

**やること**
- **F-20 画像からタグを作る**: 取り込んだ画像(ファイル / ギャラリーの画像)を、ComfyUI の WD14 Tagger で解析し、`1girl, long hair, school uniform, outdoors` のような **タグ列** を得て、プロンプト欄へ入れる。
- 結果はプロンプト欄へ入れる前に **確認・編集** できる(置き換え / 末尾に追加)。
- ComfyUI 側のカスタムノードは、アプリ内インストール(23)の **追加コンポーネント** として導入できる(既存のカスタムノードと同じ扱い)。

**やらないこと(v0.34)**
- 自然文の説明(キャプション)の生成。WD14 はタグ列のみ。自然文は将来 VLM(別設計)で扱う。
- Claude など外部サービスへの画像送信による解析(案 C)。本設計では扱わない。
- ネガティブプロンプトの自動生成。解析結果の自動適用(必ず確認してから反映する)。
- 画像のバッチ解析(複数枚の一括)、タグの辞書・自動補完、解析結果の DB 保存。
- 解析中のジョブ並行実行(§4.3。生成中は使えない)。

## 2. 要件

| ID | 機能 | 内容 |
|---|---|---|
| F-20 | 画像からタグを作る | 画像 1 枚を ComfyUI のタガーで解析し、タグ列を得る。確認・編集のうえ、プロンプト欄へ「置き換え」または「末尾に追加」する。画像は外部へ送らない。タガーのノードが無いときは、機能を無効にして導入手順を案内する |

## 3. 前提(ComfyUI 側の依存)

10 §3 の顔補正・ControlNet と同じ扱い(ノードの有無を `/object_info` で検出し、無ければ無効化して案内する)。

| 項目 | 内容 |
|---|---|
| カスタムノード | **ComfyUI-WD14-Tagger**(`github.com/pythongosssss/ComfyUI-WD14-Tagger`。コミット固定) |
| 検出 | `/object_info` に `WD14Tagger|pysssss` があること。`model` の候補(`model` の combo)も同時に読む |
| 解析モデル | SmilingWolf 製の WD タガー(`wd-v1-4-moat-tagger-v2` など。ONNX)。**初回の実行時に、ノードが Hugging Face から取得する**(§8・Q-292) |
| 追加の pip 依存 | `onnxruntime`(**CPU 版**を固定。GPU 版は PyTorch の CUDA との整合を避けるため使わない。Q-293)ほか。実装時に確定 |

- ノード名・入力名・出力の形は、固定するコミット(`9e0a6e7`)の **ソースコードで確認して確定した**(§13.1)。実機の ComfyUI での確認は未実施(§13.3)。
- ノードの導入は、**08 の開発用スクリプト(`WD14_TAGGER_COMMIT`)**と、**23 のアプリ内インストール(コンポーネント「画像のタグ付け」)** の両方に加える(§7)。

## 4. 動作

### 4.1 利用者の体験

1. 生成画面のプロンプト欄の近くにある **[画像からタグを作る]**(翻訳 34 の隣)を押す。
2. ダイアログが開く。画像を選ぶ(**[ファイルを選ぶ]** または **[ギャラリーから]**)。ギャラリー詳細の操作にも **[画像からタグを作る]** を置き、押すとその画像で同じダイアログが開く。
3. [解析する] で解析する(通常は数秒。初回は解析モデルの取得で時間がかかる旨を表示)。
4. 結果のタグ列が **編集できるテキスト欄** に出る。反映先を選ぶ: ( )置き換え / (•)末尾に追加 → **[プロンプトに入れる]**。
5. 詳細設定(折りたたみ): 解析モデル、しきい値(一般タグ・キャラクタータグ)、除外するタグ。

- ダイアログは、結果を出すだけで **プロンプト欄を自動では書き換えない**(Q-294)。
- 実行中は [キャンセル](ComfyUI の `/interrupt` ではなく、アプリ側で結果を破棄する。Q-295)。

### 4.2 パラメータ

| 項目 | キー | 既定 | 範囲 | 説明 |
|---|---|---|---|---|
| 解析モデル | `model` | `wd-v1-4-moat-tagger-v2`(候補にあればそれ。無ければ候補の先頭) | `WD14Tagger|pysssss.model` の候補 | |
| 一般タグのしきい値 | `threshold` | 0.35 | 0.05〜1.0 | 小さいほどタグが増える |
| キャラクタータグのしきい値 | `characterThreshold` | 0.85 | 0.05〜1.0 | 作品名・キャラクター名のタグ |
| 除外タグ | `excludeTags` | 空 | カンマ区切り | 出力から除きたいタグ |

- ノードのその他の引数は、アプリ内の固定値とする: アンダースコアをスペースに置換する(`replace_underscore = true`。プロンプトで一般的な表記)、末尾のカンマは付けない(`trailing_comma = false`)。
- 出力は文字列 1 つ(カンマ + スペース区切り)。レーティング系のタグ(`general` / `sensitive` / `questionable` / `explicit`)は、ノードが返す場合でも **結果の表示から除く**(Q-296。成人向けの区別はプロンプトとしては不要。プロンプト欄へ入れるのは内容を表すタグのみ)。

### 4.3 同時実行(生成ジョブとの関係)

- 解析は ComfyUI の実行キューに載る。**生成ジョブが実行中のとき(キューに実行中・待機中がある間)は開始できず**、「生成が終わってからお試しください」と表示する(`ENGINE_BUSY`。Q-297)。アプリのジョブ管理(02)が、WebSocket のイベントを自分のジョブのものとして処理しているため、別の実行を混ぜない。
- 解析中に生成を始めた場合は、既存のジョブ実行の順序に従う(ジョブは ComfyUI のキューで解析の後に回る)。解析の完了までは、生成ボタンは通常どおり押せる(待たされるだけ)。

## 5. ワークフローと結果の取り出し

```
LoadImage(image) ─ WD14Tagger|pysssss(model, threshold, character_threshold, …) ─ (出力ノード。結果は history の outputs に載る)
```

- 実行用のワークフローは Rust のコードで組み立てる(02 §3 の方針)。**SaveImage は使わない**(ギャラリーに保存しない)。
- 画像は 10 §6 と同じ経路で ComfyUI の `input/` へアップロードする(既存の `/upload/image` を使う)。
- 結果は、`/history/{prompt_id}` の `outputs[<WD14Tagger のノード ID>].tags`(文字列の配列。先頭要素)から取り出す。**この形はコミット固定のバージョンで実機確認してから確定する**(§13)。取り出せない場合は `ENGINE_BAD_RESPONSE`(既存の応答形式エラー)。
- 実行の待機・タイムアウト・エラー処理は、生成ジョブの実行層(`engine/comfyui`)の仕組みを流用し、**ジョブ(`jobs` テーブル)としては扱わない**(履歴にも残らない。Q-298)。
- 必要ノードが無ければ `ENGINE_NODE_MISSING`(`details.node = "WD14Tagger|pysssss"`。04)。

## 6. IPC・DB・UI

### 6.1 IPC(04 に追記する内容)

| コマンド | 入力 | 出力 | 説明 |
|---|---|---|---|
| `image_tag` | `{ image: string, model?: string, threshold?: number, characterThreshold?: number, excludeTags?: string }` | `{ tags: string, model: string }` | `image` は取り込み済みの参照画像のパス(`inputs/…`。既存の `input_image_pick` / `input_image_from_gallery` で取り込む。新しい取り込みコマンドは作らない)。同期的に結果を返す |

- 範囲外の値・存在しない画像は `VALIDATION` / `IMAGE_NOT_FOUND`。生成ジョブが実行中・待機中は `ENGINE_BUSY`(§4.3)。ノードが無ければ `ENGINE_NODE_MISSING`。
- `engine_status.features` に **`imageTag: boolean`**(`WD14Tagger|pysssss` の有無)を加える。解析モデルの候補は、既存のモデル一覧(`engine_models`)に **`taggers: string[]`**(`WD14Tagger|pysssss.model`。ノードが無ければ空)を追加して返す。
- DB の変更は無い(マイグレーション不要)。解析結果は保存しない。

### 6.2 UI(05 に追記する内容)

```
プロンプト  [………………………………………………]   [日本語から翻訳 ▾]  [画像からタグを作る]

┌ 画像からタグを作る ────────────────────────────┐
│ 画像: [ファイルを選ぶ] [ギャラリーから]   [サムネイル] │
│ ▸ 詳細設定(モデル・しきい値・除外タグ)               │
│                                  [解析する]         │
│ 結果(編集できます)                                  │
│ ┌──────────────────────────────────────────┐ │
│ │ 1girl, long hair, school uniform, outdoors, …  │ │
│ └──────────────────────────────────────────┘ │
│ 反映: ( )置き換え (•)末尾に追加   [プロンプトに入れる] │
│ ※ このタグは Danbooru 系のモデル(アニメ系 SDXL / Anima 等)向けです │
└───────────────────────────────────────────┘
```

- ボタンの無効条件: タガーのノードが無い(`features.imageTag` が false)。このときは [導入の案内](設定 > ComfyUI の導入コンポーネントへのリンク。管理インストールでは [追加で導入]、23 §8)を出す。
- 注記: タグ形式は、`sd15` / `sdxl` のアニメ系・Anima(タグで指示するモデル)向け。**Flux 系・Qwen-Image 2.1・Krea 2 は自然文向き** なので、現在のモデルが該当するときは注記を出す(動作は妨げない。Q-299)。
- 生成ジョブが実行中のときは [解析する] を無効にして理由を表示する。
- キーボード: ダイアログ内で Enter は改行せず、[プロンプトに入れる] は明示のボタン操作のみ。Esc でダイアログを閉じる(解析中は先にキャンセル)。
- 文言は日本語・英語(i18n。06)。

- **23(アプリ内インストール)**:
  - マニフェスト(`engine-manifest.json`)に、コンポーネント「画像のタグ付け」を追加する(コミットの zip、SHA-256 照合。08 の値と一致テストを行う)。
  - §3.1 の選択に追加: 「**画像のタグ付け**: ComfyUI-WD14-Tagger(onnxruntime を含む)。既定はオン」。サイズとディスク使用量の目安を表示する。
  - 検証(§4.2 の手順 8)に `/object_info` の `WD14Tagger|pysssss` の確認を加える(選択時のみ)。
  - [追加で導入] / [削除] で後から変更できる(§8)。
- アプリ内インストールでない(利用者が自分で用意した)ComfyUI は、ノードの導入手順(ComfyUI Manager または手動配置)をアプリ内ヘルプと README に記載する。

## 8. 通信とプライバシー

- **画像・プロンプトは外部へ送られない**。画像はローカルの ComfyUI へアップロードされるだけ(10 §6)。01 の「通信先は設定されたエンジンのみ」に対する **新しい例外は作らない**。
- **例外に近い点**: 解析モデル(ONNX と、タグの CSV)は、**ComfyUI 側のノードが初回に Hugging Face から取得する**(10 §3 の controlnet_aux の重みと同じ。アプリ自身の通信ではない)。このため **解析の初回だけ、利用者の PC の ComfyUI がインターネットへ接続する**。オフライン環境では、事前にノードのモデル置き場へ配置する(導入手順に記載)。
- アプリ内のモデル取得(12)のカタログへ、解析モデルを加える案もある(取得元・ハッシュを固定でき、許可リスト・ハッシュ検証の枠組みに乗る)。ただし、**ノードがモデルを探す場所・ファイル名はノードの実装に依存し、アプリの置き場(`models/`)とは別**(ノードのフォルダ内)なので、**今回は行わない**(Q-292。必要になれば別設計)。
- 解析結果は DB にもログにも残さない(デバッグログ(31)にもタグの中身は出さない。画像のパスも出さない)。

## 9. AI サポート(11・13 §4)への反映

- 機能カタログ(`services/assistant/capabilities.rs`)に F-20 の使いどころ(「画像からプロンプトを作りたい」→ [画像からタグを作る] の手順。タグ形式は Danbooru 系モデル向けであること、ノードの導入、反映は確認してから)を追記する。「できないこと」の「元画像からのプロンプト自動生成」は **「自然文の説明(キャプション)の生成」** に直す。
- 現在のフォームのスナップショットに **`capabilities.imageTag`(有無のみ)** を加える。**画像・タグの中身は送らない**。
- `suggest_params` のホワイトリストには加えない(19 §8 と同じ理由)。

## 10. テスト方針

- Rust: ワークフローの組み立て(LoadImage → WD14Tagger のみ。SaveImage が無い。`threshold` 等の反映、固定値(`replace_underscore`・`trailing_comma`))、結果のパース(history の `tags` から文字列を取り出す。欠落時のエラー)、レーティングタグの除去、除外タグの処理、検証(範囲外・画像の欠損・ジョブ実行中の `ENGINE_BUSY`・ノード無しの `ENGINE_NODE_MISSING`)、`engine_status.features.imageTag` と `taggers` の判定、モックサーバでの一連の流れ、ログにタグ・パスが出ないこと。実機の ComfyUI のテストは `#[ignore]`(既存方針)。
- フロント(Vitest): 反映(置き換え / 末尾に追加の区切り文字の扱い)、ボタンの無効条件、注記の出し分け(モデル種別による)、キャンセル。
- マニフェスト(23): 08 の `versions.env` との一致テスト、SHA-256 の照合。
- 手動(09 に追加): 実画像でのタグの質(しきい値の違い)、初回の解析モデル取得、オフライン時の案内、ノード未導入時の案内、生成中の無効表示、アプリ内インストールでの追加導入、macOS での onnxruntime の動作。

## 13. 実装時の判断(設計との差異)

### 13.1 ノードの仕様の確認(固定したコミット `9e0a6e700299182fc05c58b62e7ad9f72182a78b`、2025-07-11、MIT)

ソース(`wd14tagger.py`・`pysssss.json`・`requirements.txt`)を読んで、次を確認した。

- ノード名 `WD14Tagger|pysssss`。入力は `image`・`model`・`threshold`・`character_threshold`・`replace_underscore`・`trailing_comma`・`exclude_tags`。`OUTPUT_NODE = True`(SaveImage なしで実行される)。
- 結果は `{"ui": {"tags": [文字列]}}` で返るので、`/history` の `outputs[<ノード ID>].tags[0]` から取り出せる(§5 の想定どおり)。
- **`model` の候補は、導入済みかどうかに関係なく、`pysssss.json` の既知モデル 11 種 + 導入済みの追加分**(未取得のモデルも選べる。選ぶと初回にノードが取得する)。
- **レーティング(general / sensitive / questionable / explicit)は、ノードが元から出力しない**(一般タグ以降だけを返す)。§4.2 の除去処理(Q-296)は、念のための防御として残した。
- 括弧は `\(` `\)` にエスケープされて返る(SD 系のプロンプトの括弧の重み付けと衝突しないため)。アプリはそのまま通す。
- 解析モデル(`model.onnx`・`selected_tags.csv`)は、初回に Hugging Face(`SmilingWolf/*`)から `custom_nodes/ComfyUI-WD14-Tagger/models/`(または `wd14_tagger` の登録先)へ自動取得される(§8 のとおり)。
- 既定の `ortProviders` は CUDA → CPU の順。CPU 版の `onnxruntime` では CUDA が使えず、CPU にフォールバックする。

### 13.2 設計との差異

| 項目 | 設計 | 実装 |
|---|---|---|
| `onnxruntime` の固定(Q-293) | CPU 版を固定 | **CPU 版(`pip install onnxruntime` の既定)を入れるが、バージョンは固定していない**(ノードの `requirements.txt` が無指定。08 §6.1 の ultralytics と同じ扱い。導入結果の固定は必要になったときに行う) |
| タグ付けの依存の導入(アプリ内インストール) | `requirements.txt`(`onnxruntime`)を導入 | **`onnxruntime` 系(`onnxruntime-gpu` など)が venv に既にあれば、導入を飛ばす**(重ねると同じフォルダを上書きして壊れるため。顔補正・ControlNet の部品が先に入っている環境で起こる)。実機の検証中に、手で `pip install onnxruntime` を重ねて壊した経験による(`.dist-info` で判定。Rust のテストあり) |
| 導入済みの環境への追加 | (23 §8 の [追加で導入]) | **[追加で導入] ボタンを実装**(23 §8 に詳細) |
| ダイアログの [ギャラリーから] | ダイアログ内のボタン | 当初は未実装だったが、**実装済み**(設計どおり)。押すとサムネイルの一覧(新しい順・48 件ずつ、[さらに読み込む])が開き、選ぶとその画像が対象になる。ギャラリー詳細の [画像からタグを作る] からも開ける |
| 実行の待機 | 生成ジョブと同じ仕組みを流用 | 履歴のポーリングのみ(WebSocket の進捗は使わない)。上限 15 分(初回のモデル取得を見込む) |
| `ENGINE_BUSY` | 04 に記載 | 既存の `ENGINE_BUSY`(導入・管理用)のコードを流用。画面では専用の文言(`tagger.busy`)を出す |
| `ENGINE_NODE_MISSING` の `details.node` | 04 に記載 | 既存の実装どおり、メッセージにノード名を含める(`details` は持たない) |
