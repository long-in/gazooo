# 30. ローカル LLM(Qwen3.5-9B)の管理・起動・メモリ解放(v0.23)

> ステータス: 🟢 承認済み・実装済み(2026-11-21。差異は §13)。 11 §13 の「ランタイムは同梱・起動しない」方針を、本書で **「アプリが導入・起動・停止まで管理する」** に置き換える(ユーザー指示 2026-11-21)。11 §13 の他の部分(通信形式・ツール呼び出し・同意不要など)は有効。

## 1. 目的とスコープ

**やること**
- Qwen3.5-9B(GGUF 量子化)と推論ランタイム(llama.cpp の `llama-server`)を、**アプリ内から導入・更新・削除** できるようにする。
- `llama-server` の起動・停止を **Rust 側で管理** する(23・15 と同じ方式)。相談の送信時に必要なら自動起動する。
- **メモリ(RAM / VRAM)を解放する**: 一定時間使われなければ自動で停止、手動の「今すぐ解放」、画像生成の開始前の自動解放、アプリ終了時の確実な停止。
- 既存の「外部サーバに接続」(Ollama 等。11 §13)は **上級者向けの選択肢として残す**。

**やらないこと**
- Qwen3.5-9B 以外のモデルの一覧・カタログ化(導入の自動化は 9B のみ。**例外: 34 §9 の翻訳専用モデル 1 つを追加する(v0.30 追補・実装済み。34 §9.14)**)。
- Ollama のインストール・起動・メモリ管理(外部サーバのメモリはアプリでは管理しない)。
- LLM と ComfyUI の VRAM の高度な調停(§5 の単純な自動解放のみ)。
- 画像・音声入力(テキストのみ)。

## 2. ランタイムの選定(推奨: llama.cpp)

| 観点 | llama.cpp `llama-server`(採用) | Ollama |
|---|---|---|
| アプリからの制御 | 単一バイナリをアプリが取得・起動・終了でき、**プロセス終了で確実にメモリが空く** | 別インストーラ・常駐サービスで、起動・終了をアプリが管理しにくい |
| モデル | GGUF を既存のダウンロード基盤(12)で取得・ハッシュ検証 | 独自のモデル保管 |
| 新モデル対応 | 速い | 遅れることがある |
| 起動オーバーヘッド | 起動のたびにモデルを読む(数秒〜十数秒。OS のファイルキャッシュで 2 回目以降は短縮) | 常駐で速い |

→ 「アプリで管理 + メモリ解放を確実に」を満たすため llama.cpp を採用する。再読み込みの待ち時間は、パネルに「モデルを読み込み中…」と表示して許容する。

## 3. 導入物と保存先

保存先: `{app_data_dir}/llm/`(23 の `comfyui/` と同様に、アプリのデータ領域に閉じる)。

```
llm/
  bin/<llama.cpp ビルド番号>/   # llama-server(.exe) と依存 DLL / dylib
  models/Qwen3.5-9B-<量子化>.gguf
  .gazooo-llm.json              # 導入済みバージョン・ファイルの SHA-256 の印
```

固定マニフェスト(`src-tauri/src/services/llm/manifest.json`。23 §3 と同じ考え方で、**バージョン・URL・SHA-256 を固定**。実際の値は §13):

| 項目 | 内容 |
|---|---|
| ランタイム | llama.cpp の公式リリース(GitHub Releases)のビルド番号を 1 つ固定。Windows x64 は GPU 版(CUDA または Vulkan。**実機で選定して確定**)と CPU 版、macOS は Apple Silicon(Metal) |
| モデル | Qwen3.5-9B の GGUF。**量子化は Q4_K_M を既定**(目安 5〜6GB)。配布元の Hugging Face リポジトリ・ファイル名・サイズ・SHA-256 は **実機で確認して確定**(確認までは仮置き) |
| 許可ホスト | `github.com` / `objects.githubusercontent.com`(ランタイム)、`huggingface.co`(モデル)。12 の許可リスト方式に追加 |

- ダウンロードは 12 の基盤を再利用(再開・ハッシュ検証・進捗・キャンセル)。ハッシュ不一致は破棄して `LLM_INSTALL_HASH_MISMATCH`。
- 導入は冪等(完了した手順は印で飛ばす。23 §4.2)。
- **更新**: アプリの更新でマニフェストが変わったとき、設定に「更新があります」を出す。自動では更新しない。
- **削除**: 「LLM を削除」で `llm/` を丸ごと削除(確認つき)。停止中のみ可。

## 4. 起動と停止(`LlmProcess`。15 の `EngineProcess` と同型)

状態: `not_installed` / `stopped` / `starting` / `ready` / `stopping` / `error`。

起動:
- 呼び出し元は (a) 相談の送信時(`provider=local` で `stopped` のとき自動)、(b) 設定の「起動」ボタン。
- コマンド: `llama-server -m <gguf> --host 127.0.0.1 --port <空きポート> --jinja -c <コンテキスト長> -ngl <GPU 層数>`。
  - **ポートは起動のたびに空きポートを選ぶ**(ループバックのみ。外部に公開しない)。
  - `--jinja`: ツール呼び出し(11 §13.3)に必要。
  - コンテキスト長・GPU 層数・再試行の実際の値は §13.2(コンテキスト 16384、`-ngl` は自動調整、失敗時は GPU なしで 1 回だけ再試行)。それでも失敗なら `LLM_START_FAILED`(原因の要約をログ末尾から表示)。
- 準備完了は `GET /health` が 200 になるまでポーリング(タイムアウト 120 秒)。読み込み中は `starting`。
- 起動中の相談の送信は、準備完了まで待つ(UI は「モデルを読み込み中…」)。起動に失敗したら `LLM_START_FAILED`。

停止:
- 子プロセスを終了(まず通常終了、一定時間で強制終了。Windows は子プロセスツリーごと。15 §6 と同じ)。**プロセスが終われば RAM / VRAM は OS に返る**。
- 相談のストリーミング中は自動停止しない。手動の「今すぐ解放」は、相談中なら中断してよいか確認する。
- アプリ終了時は必ず停止する(02 の終了処理に追加)。異常終了に備え、起動時に前回の子プロセス(PID ファイル)が残っていれば終了させる(15 と同方式)。

ログ: `llama-server` の標準出力・標準エラーはメモリ上のリングバッファ(直近 N 行)に保持し、設定の「ログを表示」で見られる。**プロンプト・回答本文はログに出さない**(llama-server がリクエスト本文を出すかを実機で確認し、出る場合は起動オプションで抑止する)。

## 5. メモリの解放

| 契機 | 挙動 |
|---|---|
| **アイドルタイムアウト** | 最後の相談の完了から一定時間で自動停止。選択肢: 1 分 / **5 分(既定)** / 15 分 / 30 分 / 無効(手動のみ)。`settings` の `llm.idle_minutes` |
| **今すぐ解放** | 設定・AI パネルの [メモリを解放] で即停止(`ready` / `starting` のとき有効) |
| **画像生成の前** | ジョブキューが生成を始める直前に LLM が `ready` / `starting` なら自動停止して VRAM を空ける。設定 `llm.release_before_generation`(**既定: 有効**)。次の相談の送信時に自動で再起動する |
| **アプリ終了** | 必ず停止(§4) |

- パネルとステータスバー(29)に LLM の状態(停止中 / 読み込み中 / 準備完了 / メモリの目安)を小さく表示する。メモリの目安はモデルのファイルサイズからの概算でよく、厳密な計測はしない。

## 6. プロバイダとの関係(11 §13 の更新)

`assistant.provider` を 3 値にする: `anthropic` / `local`(アプリ管理)/ `local_external`(外部サーバ。Ollama 等。11 §13.1 の接続先 URL・モデル名・ループバック制限・接続確認をそのまま適用)。

- `local`(管理): 接続先は `LlmProcess` が決めた `http://127.0.0.1:<port>/v1`。ユーザーが URL を入力する欄は出さない。
- 通信・SSE・`tool_calls`・思考出力の無効化・同意不要・プライバシーは 11 §13.2〜13.3 のとおり(`local` と `local_external` で共通)。
- 未導入で `local` の相談は `LLM_NOT_INSTALLED`(UI は導入ウィザードへ案内)。

- VRAM が足りない(目安 8GB 未満)場合は、遅くなることを警告する。

`settings` に追加: `llm.idle_minutes`(number、既定 5)/ `llm.release_before_generation`(boolean、既定 true)。`assistant.provider` の値に `local_external` を追加(11 §13.5)。導入状態は DB でなく `.gazooo-llm.json` から読む。

## 10. 実装方針(承認後)

- Rust: `services/llm/{mod.rs, manifest.rs, installer.rs, process.rs}` と `commands/llm.rs`。12 のダウンロード基盤・23 のインストーラ・15 のプロセス管理の部品を再利用し、新規依存は原則なし。ジョブキュー(`services/jobs.rs`)の生成開始フックに「LLM の自動解放」を追加。`services/assistant` は `local` のとき `LlmProcess::ensure_ready()` を呼んでから OpenAI 互換クライアント(11 §13.8)で送信。
- フロント: `src/lib/tauri/llm.ts`、設定の「ローカル LLM」セクション、パネル・ステータスバーの状態表示。i18n は ja / en。
- OS 差: パス・実行ファイル名・DLL / dylib・プロセスツリー終了は 06 に従い分離。
- テスト(Rust): マニフェストの整合・ハッシュ不一致の破棄・空きポート選択・`/health` 待ちのタイムアウト・アイドル自動停止(時計を差し替えて)・ストリーミング中は停止しない・生成開始前の解放・終了時と起動時の残存プロセスの後始末(モックの子プロセスで)。実機の導入と Qwen3.5-9B での相談は `#[ignore]`。
- 09 の手動チェックに「導入・起動・相談・自動停止・手動解放・生成前の自動解放(実際に RAM / VRAM が減ること)・削除・外部サーバ接続」を追加する。

## 12. 受け入れ基準

- 設定から Qwen3.5-9B とランタイムを導入でき、ハッシュ検証が通る。導入後の相談は外部に通信しない。
- 相談の送信で自動起動し、回答が逐次表示される。提案カードも出る(モデルが対応する場合)。
- アイドルのタイムアウトで自動停止し、**プロセスが消えて RAM / VRAM が解放される**。手動の解放・生成前の自動解放・アプリ終了時の停止も働く。
- 異常終了後の再起動で、残った子プロセスが終了される。
- 外部サーバ(`local_external`)への接続は従来の設計どおり使える。

### 13.1 確定した値(§3 の「実機で確定」の結果)

| 項目 | 値 |
|---|---|
| ランタイム | llama.cpp **b12426**(MIT)。Windows x64 は **Vulkan 版**(`llama-b12426-bin-win-vulkan-x64.zip`、約 38MB。CUDA 版は CUDA ランタイムの同梱が別途必要で約 630MB になるため見送り)、macOS は Apple Silicon 版(Metal。`llama-b12426-bin-macos-arm64.tar.gz`、約 17MB) |
| モデル | `unsloth/Qwen3.5-9B-GGUF` の **`Qwen3.5-9B-Q4_K_M.gguf`**(Apache-2.0、5,680,522,464 バイト)。URL はリビジョン `3885219b…` に固定 |
| 検証 | SHA-256 はマニフェストに固定(GitHub の `digest` と Hugging Face の LFS の値で確認済み)。ビルド番号・リビジョンが URL に含まれることを単体テストで確認 |
| 許可ホスト | `github.com` / `objects.githubusercontent.com` / `release-assets.githubusercontent.com` / `huggingface.co` / `hf.co`(Hugging Face の CDN は `*.hf.co`) |

### 13.2 設計からの差異

| 項目 | 設計 | 実装 |
|---|---|---|
| 起動引数 | `-c 8192 -ngl 99` | **`-c 16384`**(システムプロンプト約 8,000 文字 + フォーム + 履歴 + 回答でも溢れないように)。**`-ngl` は指定せず** `llama-server` の自動調整(`--fit`)に任せる。ほかに `-np 1`(スロットを増やさない)、**`-cram 0`**(プロンプトのキャッシュをメモリに溜めない。既定は最大 8GB でメモリ解放の方針に反する)、`--chat-template-kwargs {"enable_thinking":false}` |
| 起動失敗の再試行 | 層数を減らして 1 回 | **GPU を使わず(`-ngl 0`)に 1 回だけ再試行**し、それでも失敗なら `LLM_START_FAILED` |
| 異常終了後の残存プロセス | PID ファイルで起動時に後始末 | **PID ファイルは作らない**。15 と同じく、子プロセスを Windows の Job Object / Unix のプロセスグループに入れ、アプリが落ちたときは OS が終了させる(`EngineProcess` を再利用) |
| 導入ウィザード | 事前チェック → 同意 → 取得 → 完了の画面遷移 | **同意ダイアログ 1 つ**(取得元・サイズ・ライセンス・VRAM の注意)+ 設定画面内の進捗表示。事前チェックは空き容量のみ(GPU / VRAM の検出はしない) |
| ステータスバーへの表示 | あり(29) | **なし**(設定画面と相談パネルの状態表示のみ。ステータスバーは必要になったら別途) |
| 生成前の自動解放 | 起動中・読み込み中なら停止 | 同じ。ただし **回答の生成中は止めない**(§4 の方針どおり。回答後のアイドル停止か次の生成で解放) |
| ログ | リングバッファ + 設定で表示 | 同じ(`llama-server` の出力は `llm.log` にも書く。プロンプト・回答本文は出ないことを実機で確認) |
| `llm_install` の戻り値 | `{ installId }` | 同じ。進捗のペイロードは `InstallState`(`installId` / `status` / `step` / `totalSteps` / `stepId` = `runtime` \| `extract` \| `model` / `received` / `total` / `error`) |
| `llm_update_settings` の引数 | `{ idleMinutes?, releaseBeforeGeneration? }` | 同じ(`idleMinutes` は 0 / 1 / 5 / 15 / 30 のみ。それ以外は `VALIDATION`) |
| システムプロンプト(11 §12 の初期値) | – | ローカル LLM に合わせて更新: 「AI に相談」の送信先(Claude / ローカル / 外部サーバ)とメモリ解放の案内を機能カタログに追加、回答を短くしてツール引数をスキーマどおりにする指示、**参照画像を使う成人向けの依頼は「成人の架空キャラクター(イラストや CG)」とユーザーが説明したときに限り、実在の人物・未成年に見える画像は協力しない**ルール(モデル提案のルール)。未編集の利用者は自動で最新になり、編集済みの利用者は「初期値に戻す」で反映 |
| 追加の IPC | – | `assistant_local_check { baseUrl?, model? }`(11 §13.6)。`LlmStatus` に `supported` / `updateAvailable` / `downloadMb` / `runtimeLicense` / `modelLicense` / `message` を追加 |

### 13.3 検証(実機の Windows 11・RTX 2060 12GB)

- `llama-server`(b12426 Vulkan)+ Qwen3.5-9B Q4_K_M を、上の起動引数で起動できる(読み込み約 10 秒)。`/health` → 200、`/v1/chat/completions` のストリーミングで **`tool_calls` が断片で届き**、思考は出力されない。プロセスを終了すると GPU のメモリが約 5.3GB 解放されることを `nvidia-smi` で確認した。
- 実際のシステムプロンプト・提案ツール付きで、`AssistantService` から `Provider::Local` で相談 → 回答の逐次表示と `suggest_params` の提案(検証済み)→ アイドル停止でプロセス消滅、までを 1 テスト(`#[ignore]`、`GAZOOO_LLM_E2E_RUNTIME_DIR` / `GAZOOO_LLM_E2E_MODEL`)で確認した(コールドスタートから応答完了まで約 11 秒)。
- 自動テスト: Rust 361 件(マニフェスト・導入(ハッシュ不一致・中止・再実行)・起動と再試行・アイドル停止・生成前解放・削除・プロバイダの振り分け・ループバック検証・SSE と `tool_calls` の結合・思考の除去・生成フック)、Vitest(画面の判定ロジックとストア)、`cargo clippy -D warnings`・ESLint・`next build`。
- **未確認**: アプリ UI の目視確認(導入ダイアログ・進捗・解放ボタン)、アプリ内の `llm_install` による実際のダウンロード(5.7GB。導入処理は 12 の基盤と同じで、ローカルのテストサーバでは確認済み)、macOS(Metal 版)、Ollama など外部サーバとの実接続。

## 14. 追補(v0.30・実装済み): 翻訳専用モデルの追加

34 §9 のため、マニフェストの `models` を配列にして `role`(`assistant` / `translate`)を持たせ、翻訳専用モデルを 1 つ追加する。ランタイム・ダウンロード基盤・起動管理・アイドル停止・生成前解放は共有する。**同時に起動するモデルは 1 つ**で、必要なモデルが変わるときは停止 → 起動で切り替える。起動引数(§13.2 の `enable_thinking` など)はモデルごとにマニフェストで持つ。`llm_status` / `llm_install` / `llm_remove` は `role` を受け取る。詳細は 34 §9.4・§9.5。銘柄は 34 §9.4(Q-232)の実機比較で確定する。
