# 35. バックアップ(取得とインポート)(v0.29)

> ステータス: 🟢 承認済み・実装済み(2026-11-21。07 Q-212〜227 は回答反映済み。Rust・Vitest・clippy・ESLint・ビルドまで確認。画面の目視確認・Windows 実機での取得/復元・macOS は未実施)。§14 に実装時の判断(設計との差異)を記載する。

## 1. 目的とスコープ

設定値・ギャラリー・プロンプトなどの入力データを **1 つのファイルにまとめて保存(バックアップ取得)** し、あとから **読み込んで復元(インポート)** できるようにする。PC の入れ替え・再インストール・誤操作からの復旧が目的。操作は **設定 > 「その他」タブ**(31 §5 で新設)に置く。

**バックアップの対象(3 区分。それぞれトグルで ON / OFF。既定はすべて ON)**

- **設定値**: アプリの設定と、入力データのうち「個人の下書き」に当たるもの。
- **ギャラリー**: 生成した画像と、その再現に必要なジョブの設定(プロンプト・パラメータ)。
- **プリセット**: 保存したプリセット。

区分は互いに独立で、**取得も復元も区分ごとに選べる**(§4)。


| 区分(トグル) | 内容 | 保存場所(現状) |
|---|---|---|
| **設定値** | `settings` テーブル(テーマ・言語・AI サポート・プロンプト翻訳・LLM の設定、`ui.state`、生成の既定値、**生成フォームの下書き**、モデル取得の同意、**画像保存先・ComfyUI の起動管理のパス・モデル保存先・デバッグ**など。API キーのみ §2 のとおり別扱い)、AI サポートの会話履歴(`assistant_*`) | `gazooo.db` |
| **ギャラリー** | `jobs`(`params_json`・`prompt_text` = 「この設定で生成」の元)と `images`、原寸画像、サムネイル、参照画像・マスク(`inputs/`。ジョブの再現に必要) | `gazooo.db` と画像保存先 |
| **プリセット** | `presets` テーブル | `gazooo.db` |

- プリセットが参照する参照画像(`presets.params_json` 内の `inputs/…`)は、**プリセットの区分に含めず**、ギャラリーの区分(`inputs/` 一式)に入る。ギャラリーを OFF にして取得したバックアップでは参照画像が無いため、復元後にそのプリセットを使うと「参照画像が欠損」として扱われる(10 §8 と同じ。トーストで知らせる)。この旨を UI に注記する。
- 会話履歴は「入力データ」だが、AI サポートの設定と同じく個人の使い方に属するため、**設定値に含める**(07 Q-224)。

**対象外(やらないこと)**
- ComfyUI 本体・Python・モデルファイル(数十 GB になりうる。再取得は 12・23 の機能で行う)。
- ローカル LLM(30)のモデル・`llama-server`。
- ログ(31 の ZIP 取得で別に行う)。
- 自動バックアップ・定期バックアップ・クラウド同期(手動のみ)。
- 差分・増分バックアップ(毎回フルで取得する)。
- 他のアプリ(ComfyUI のワークフロー等)の形式との互換。

## 2. 設定値の扱い(端末依存の設定・API キー)

- **端末依存の設定も、他の設定と同じくバックアップに含めて、そのまま復元する**(画像保存先 `storage.images_dir`、ComfyUI の起動管理 `engine.comfyui.managed` の `main.py`・Python・base-directory・引数、モデル保存先 `engine.comfyui.models_dir`、`debug.enabled`)。復元した値のパスが **この PC に存在しなくても、そのまま復元する**(07 Q-214)。
  - 別 PC では、ComfyUI の起動管理が起動できない・モデル保存先が見つからない状態になりうる。これは設定 > エンジン / 保存先の通常のエラー表示で分かり、導入し直し(23)・自動検出(22)・手動設定で直せる。
  - 画像保存先が存在しない場合は、**復元時に `create_dir_all` で作成する**(ギャラリーの画像を置くため)。アプリ起動時の処理(`lib.rs` の画像保存先の作成とスコープ許可)は変更しない。
  - **設定値を復元し、ギャラリーを復元しない**場合に画像保存先がバックアップの値に変わると、現在のギャラリーの相対パスが新しい保存先に無く、画像が表示できなくなる。**確認ダイアログで、その組み合わせのときに警告を出す**(「画像保存先が変わるため、現在のギャラリーの画像が表示されなくなる可能性があります。ギャラリーも復元するか、保存先の設定を残してください」)。
- **API キー(`assistant.api_key`・`assistant.key_verified`)だけは別扱い**: 既定ではバックアップに含めない。設定値が ON のときだけ、チェックで含められる(§4。07 Q-215・Q-227)。平文の秘密情報で、ファイルを他人に渡しうるため。
- 除外するキーは API キーの 2 つのみ。ほかは **除外リスト方式**(将来の設定キーが既定でバックアップされるようにする)。除外リストは Rust 側の 1 か所の定数に集約し、テストで固定する。

## 3. ファイル形式

- 拡張子 `.gazooo-backup`(中身は **ZIP**。31 のログ取得と同じ既存の `zip` クレートを使う)。ファイル名の既定は `gazooo-backup-YYYYMMDD-HHMMSS.gazooo-backup`(時刻は UTC。31 と同じ)。
- 画像は PNG・JPEG で既に圧縮済みのため、画像は **無圧縮(Stored)** で入れる(速度優先)。`manifest.json` と DB のダンプは Deflate。

```
manifest.json            # 形式バージョン・アプリのバージョン・DB スキーマ版・作成日時・含めたもの・件数
db/gazooo.db             # 一貫した DB のスナップショット(§3.1)
images/2026/11/<id>.png  # 原寸(images_dir からの相対パスをそのまま)
images/thumbs/<id>.jpg   # サムネイル(§3.2)
images/inputs/<uuid>.png # 参照画像・マスク
```

`manifest.json`:

```json
{
  "format": 1,
  "app": "gazooo",
  "appVersion": "0.x.y",
  "schemaVersion": 3,
  "createdAt": 1795000000000,
  "include": { "settings": true, "gallery": true, "presets": true, "apiKey": false },
  "counts": { "settings": 42, "conversations": 12, "jobs": 120, "images": 340, "inputs": 15, "presets": 8 },
  "bytes": { "images": 1234567890 }
}
```

### 3.0 区分と ZIP の中身

- OFF の区分のデータは、**ZIP にも DB スナップショットにも入れない**。スナップショットは、作成後に **OFF の区分のテーブルを空にする**(設定値 OFF → `settings` と `assistant_*`、ギャラリー OFF → `jobs`・`images`、プリセット OFF → `presets`)。
- **3 つとも OFF のときは [バックアップを保存…] を無効にする**(最低 1 つ必要)。
- スナップショットのスキーマは常に現在のもの(空の区分は空のテーブル)。`manifest.json` の `include` に、どの区分が入っているかを記録する。
- 外部キーの関係: `images` → `jobs`(CASCADE)のため、`jobs` と `images` は **ギャラリーとして常に一緒**に扱う(分けられない)。

### 3.1 DB のスナップショット

- 生成・書き込み中でも壊れないよう、**稼働中の DB を直接コピーしない**。SQLite の **`VACUUM INTO '<一時ファイル>'`**(または `rusqlite` の backup API)で、一貫したスナップショットを一時ファイルに作り、ZIP へ入れる。WAL のまま `gazooo.db` をコピーしてはならない。
- スナップショットを作ったあと、**一時ファイル上のコピーに対して** API キーを含めないときの `assistant.api_key`・`assistant.key_verified`(§2)を `settings` から削除する。稼働中の DB は変更しない。
- 取得中に生成が進んでもよい(ブロックしない)。スナップショット作成後に追加された画像は、DB の記録には無いので、画像ファイルを入れる対象は **スナップショットの `images` テーブルが参照するファイルと、`inputs/` が参照するファイル** に限る(DB に無いファイルは入れない)。

### 3.2 画像・サムネイル・参照画像

- **ギャラリーが ON のときは、画像ファイルも含める**(区分の ON = 記録と画像の両方。別トグルにはしない。「画像なしのギャラリー」は復元後に表示が壊れた状態になるため)。ギャラリーを OFF にすれば、画像は一切含めない。
- **サムネイルも含める**(ギャラリー ON のとき。別トグルにはしない。07 Q-216)。復元直後からギャラリーをすぐ表示できる。サムネイルが欠けている画像は、これまでどおり起動時のバックフィル(03)で再生成される。
- 参照画像(`inputs/`)は、ギャラリーが ON のときのみ入れる。
- ファイルが欠けている画像(DB にあるがディスクに無い)は、**スキップして件数を記録**する(取得は失敗にしない)。完了時に「N 件は見つからず含められませんでした」を知らせる。

```
バックアップ

│          アプリの設定・フォームの下書き・AI サポートの会話   │
│          [ ] API キーを含める                             │
│          ⚠ キーが平文でファイルに入ります。取り扱いに注意。 │
│ [ ●─ ] ギャラリー  340 枚 / 約 2.4 GB                    │
│          画像と、再現用のプロンプト・設定(参照画像を含む)   │
│ [ ●─ ] プリセット  8 件                                  │

```

### 4.1 取得

1. [バックアップを保存…] → Rust 側で保存ダイアログ(既定のファイル名は §3)。キャンセルは何もしない。
2. 実行中は **進捗(ファイル数 / 総数)** をバー表示し、[キャンセル] を出す。キャンセル時は書きかけの ZIP を削除する。
3. 完了時にトースト「バックアップを保存しました(N 枚・約 X GB)」+ [フォルダを開く]。含められなかったファイルがあれば件数を併記。
4. 保存先ドライブの空き容量が足りずに書き込みが失敗した場合は、書きかけのファイルを削除して `BACKUP_NO_SPACE` を返す(実装時の判断: 空き容量の取得に新規依存が必要なため、事前チェックは行わない。§14)。
5. **保存先を画像保存先やアプリのデータ領域の中にすることは拒否する**(自分自身を含む再帰・復元時の上書きを避ける)。

見込みサイズ・件数は、セクションを開いたとき・トグルの切り替え時に取得する(`backup_estimate`。ファイルのメタデータの合計のみで、読み込みはしない)。

### 4.2 復元(インポート)

1. [バックアップを選んで復元…] → ファイル選択ダイアログ(`.gazooo-backup`)。
2. **内容の検査(プレビュー)**: ZIP を開き、`manifest.json` を読んで次を表示する確認ダイアログを出す。
   - 作成日時・作成したアプリのバージョン・含まれる区分と件数(設定値・ギャラリー・プリセット)・API キーの有無。
   - **区分ごとのトグル**(バックアップに含まれる区分のみ有効。既定はすべて ON)。**復元する区分を選べる**(例: プリセットだけ戻す)。含まれない区分は無効表示で「このバックアップには含まれていません」。API キーを含むバックアップでは、「API キーも復元する」を別チェック(既定 ON。設定値が ON のときのみ)。
   - ギャラリーを復元するとき: **「バックアップに無い画像ファイルを削除する」**(既定 OFF)。ON のとき、復元後の DB が参照しない画像保存先のファイル(原寸・サムネイル・参照画像)を、**ゴミ箱へ移す**(完全削除はしない。既存の保存先変更と同じ扱い。04)。確認ダイアログに対象の件数と容量を表示する。
   - 設定値を復元しギャラリーを復元しない場合、画像保存先の変更の警告(§2)。
   - 形式が不正・`format` が未対応・**DB スキーマ版が現在より新しい**(新しいアプリで作ったバックアップ)場合は、ここでエラーにして何も変更しない(`BACKUP_UNSUPPORTED`)。古いスキーマは、復元後に通常のマイグレーション(02・03)で上げる。
3. 確認ダイアログに **復元方法の説明** を出す: 「選んだ区分の現在のデータは、バックアップの内容に **置き換えられます**(選ばなかった区分は変わりません)。**この操作は元に戻せません。** 必要なら、先に現在のデータのバックアップを取ってください。」[復元する] [キャンセル]。
4. 実行: §4.3 の手順。進捗バー表示。
5. 完了後、**アプリを再起動する**(DB 接続・画像保存先のスコープ・各サービスの状態を初期化し直すため。確認ダイアログで [再起動] を押させる。Tauri の `restart` を使う)。

### 4.3 復元の手順と安全策

**復元の前に、現在のデータの自動バックアップは取らない**(07 Q-219。ユーザー判断)。そのため UI で「元に戻せない」ことを明示する(§4.2)。ただし、**入れ替えの途中の失敗で、現在のデータが壊れた状態にならない**ことは守る(下記 1〜4)。

1. **ステージング(検査)**: バックアップを展開して検査する。`app_data_dir/restore-staging/` に DB と画像を展開し、DB は `PRAGMA integrity_check` と `user_version` を確認する。ZIP 内のパスは **正規化して `..`・絶対パス・ドライブ文字・シンボリックリンクを拒否**(Zip Slip 対策)。展開先は画像保存先の外のステージングに限る。**ここまでで失敗したら、現在のデータは何も変更しない。**
2. **ジョブを止める**: 実行中・待機中のジョブがある場合は、確認のうえ **キューを一時停止し、待機中をすべて取り消し、実行中のジョブも取り消して終了を待つ**(最大 30 秒)。生成の最中は復元しない(確認なしでは `BACKUP_BUSY`)。(実装時の判断: ブロック対象はジョブに絞る。§14)
3. **入れ替え**: 次の順で行う。
   1. 画像(**ギャラリーを復元する場合のみ**): ZIP から、**復元後の設定の画像保存先**(設定値を復元するならバックアップの値、しなければ現在の値。無ければ作成)へ **追加のみで直接展開** する(同名は上書き。`id` が UUID のため通常は衝突しない)。この段階の失敗・キャンセルは、画像が増えるだけで現在のギャラリーは壊れない。
   2. DB: **稼働中の接続に、ステージングした DB を `ATTACH` し、1 つのトランザクションで** 選んだ区分のテーブルだけを置き換える(`DELETE` → `INSERT … SELECT`。両方に存在する列のみ。設定値 = `settings`・`assistant_*`、ギャラリー = `jobs`・`images`、プリセット = `presets`。選ばなかった区分は現在のまま)。失敗すればトランザクションがロールバックされ、現在の DB は変わらない(ファイルの差し替えはしない)。API キー(`assistant.api_key`・`assistant.key_verified`)は、復元しない選択のときは現在の値を維持し、復元する選択でバックアップに無いときも現在の値を維持する。
   3. 「バックアップに無い画像ファイルを削除する」が ON なら、復元後の DB が参照しないファイルをゴミ箱へ移す(§4.2)。
4. **途中で失敗したとき**: 手順 3 の 1 の失敗は追加済みの画像が残るのみ。2 の失敗はロールバックされる。エラーを表示し、再起動は不要。**復元前の自動バックアップも、`gazooo.db.pre-restore` のような退避ファイルも作らない**(トランザクションが巻き戻しを担う)。
5. ステージングを削除して、再起動を促す(`backup_restart`。Tauri の `AppHandle::restart`)。再起動時のマイグレーション(0004 以降があれば)は通常どおり実行される。
6. **孤立ファイル**: 復元で画像保存先に残る「DB に載っていないファイル」は、ギャラリーには出ない。**自動では削除しない**。上記のオプションを選んだときだけゴミ箱へ移す(07 Q-221)。

### 4.4 マージではなく置き換え

**インポートは「置き換え」のみ** にする(マージはしない)。マージは ID 衝突・プリセット名の一意制約・会話の重複・ジョブ位置の整合を扱う必要があり、設計と検証が大きくなるため。「別の PC のギャラリーを今の PC に足す」ユースケースは今回は扱わない(07 Q-218)。

## 5. エラー(04 のエラーコードに追加)

| code | 意味 | 表示 |
|---|---|---|
| `BACKUP_UNSUPPORTED` | 形式が不正、または未対応のバージョン(新しいアプリで作成) | ダイアログ(アプリの更新を案内) |
| `BACKUP_CORRUPT` | ZIP・DB が壊れている(`integrity_check` 失敗・manifest 不整合) | ダイアログ |
| `BACKUP_BUSY` | 生成・ダウンロード・インストール・LLM の実行中 | ダイアログ(終了後に再実行) |
| `BACKUP_NO_SPACE` | 空き容量不足 | ダイアログ(必要容量を表示) |
| `BACKUP_PATH_INVALID` | 保存先がアプリのデータ領域内など | トースト |

その他の失敗は `INTERNAL`(詳細はログ。プロンプト本文・API キーは出さない。02 §3.8)。

## 6. IPC(04 に追記する内容)

| コマンド | 入力 | 出力 |
|---|---|---|
| `backup_estimate` | `{ include: BackupInclude }` | `{ settings: number; conversations: number; jobs: number; images: number; presets: number; bytes: number }`(`BackupInclude = { settings: boolean; gallery: boolean; presets: boolean }`) |
| `backup_export` | `{ include: BackupInclude; includeApiKey: boolean }`(3 つとも false は `VALIDATION`。`includeApiKey` は `include.settings` が true のときのみ有効) | `{ path: string; images: number; skipped: number; bytes: number } \| null`(Rust 側で保存ダイアログ。キャンセル時 `null`) |
| `backup_inspect` | – | `BackupManifest \| null`(Rust 側でファイル選択ダイアログ → 検査。キャンセル時 `null`。選択したパスは Rust 側が保持し、続く `backup_restore` で使う) |
| `backup_orphans` | `{ include: BackupInclude }` | `{ count: number; bytes: number }`(`backup_inspect` 済みのバックアップを復元した場合に、「バックアップに無い画像ファイル」になるものの数と容量) |
| `backup_restore` | `{ include: BackupInclude; restoreApiKey: boolean; stopJobs: boolean; deleteOrphans: boolean }`(`include` は検査したバックアップに含まれる区分の部分集合のみ。含まれない区分の指定は `VALIDATION`) | `{ restartRequired: true }`(`backup_inspect` で検査済みのファイルを復元) |
| `backup_cancel` | – | `void`(取得・復元の中断。復元は DB の入れ替えの開始前のみ中断可) |
| `backup_restart` | – | `never`(アプリを再起動する) |

- イベント: `backup:progress` `{ phase: "snapshot" \| "files" \| "staging" \| "swap"; done: number; total: number }`。
- フロントが任意のパスを渡す口は作らない(パスは Rust 側のダイアログで得る。31 と同じ)。
- `backup_restore` は **`backup_inspect` の結果を持つ状態でしか実行できない**(検査なしでの復元を防ぐ)。

## 7. 実装方針(承認後)

- Rust:
  - `services/backup/{mod.rs, export.rs, restore.rs, manifest.rs}` と `commands/backup.rs`。
  - 取得: `VACUUM INTO` → 除外キーの削除 → ZIP(`zip` 9.7.3、`deflate` のみ。画像は `Stored`)。ファイルは **ストリームで書く**(数 GB をメモリに載せない)。同期 API のため `spawn_blocking`。
  - 復元: §4.3 の手順。DB の入れ替えは `ATTACH` + 1 トランザクション(`gazooo.db` のファイル操作をしない)。
  - **新しい依存は追加しない**(`zip` は導入済み・`Stored` は `deflate` feature 不要。Tauri の `restart` は標準)。追加が必要になれば別途承認を得る(AGENTS.md §2)。
  - パスは `std::path` / `Path::join` のみ。Windows の長いパス・大文字小文字の違いに注意(ZIP 内は常に `/` 区切り)。
- フロント: `components/settings/backup-section.tsx`(`other-section.tsx` から呼ぶ)、`src/lib/tauri/backup.ts`(薄いラッパー)、`settings.backup.*` の i18n(ja / en)。
- 03: スキーマ変更・マイグレーションなし(`settings` のキー追加もなし)。

## 8. テスト

- Rust:
  1. 取得 → 復元の往復で、`settings`・`presets`・`assistant_*`・`jobs`・`images` が一致する(除外キーを除く)。
  1b. **区分のトグル**: 各区分を単独で OFF にして取得すると、その区分のテーブル・ファイルが空で、他は入る。3 つとも OFF は拒否。ギャラリー OFF では画像・`inputs/` が ZIP に無い。
  1c. **区分を選んだ復元**: プリセットだけ復元すると、`settings`・`jobs`・`images` は現在のまま(画像ファイルも追加コピーされない)。区分ごとに同様。バックアップに含まれない区分の指定を拒否。
  2. **API キーだけが ZIP の DB に含まれない**(`assistant.api_key`・`assistant.key_verified`)。`includeApiKey` のときだけ含まれる。`storage.images_dir`・`engine.comfyui.managed`・`engine.comfyui.models_dir`・`debug.enabled` は含まれる。
  3. 端末依存の設定が **バックアップの値で復元される**(存在しないパスでも)。画像保存先が存在しなければ作成され、画像がそこへ置かれる。API キーは、復元しない選択・バックアップに無い場合は現在の値が維持される。設定値のみ復元でギャラリーを復元しないとき、保存先が変わる警告が出る(フロント)。
  3b. **孤立画像の削除**: オプション OFF では孤立ファイルが残る。ON では復元後の DB が参照しないファイルだけがゴミ箱へ移り、参照されるファイル(原寸・サムネイル・`inputs/`)は残る。
  4. WAL を使う DB(書き込み中を想定)でも、スナップショットが `integrity_check` に通る。
  5. ギャラリー ON で画像が欠けていても取得が失敗せず、`skipped` に数えられる。
  6. Zip Slip(`../`・絶対パス・ドライブ文字)を含む ZIP を拒否する。巨大な展開(上限を超える展開サイズ)を拒否する。
  7. 新しいスキーマ版・不正な manifest・壊れた ZIP を `BACKUP_UNSUPPORTED` / `BACKUP_CORRUPT` で拒否し、**現在のデータが変わらない**。
  8. 入れ替えの途中で失敗した場合(DB の置き換えの失敗を注入)にトランザクションがロールバックされ、元の DB・設定に戻る。
  9. 復元の前に自動バックアップが **作られない**(`backups/` などが生成されない)。
  10. ジョブ実行中は `BACKUP_BUSY`(または確認のうえ停止)。
- フロント(Vitest): 「その他」タブにセクションが出る、3 つのトグルの既定がすべて ON で、状態が `backup_export` の引数に反映される(3 つとも OFF で保存ボタンが無効)、API キーのチェックは設定値が OFF のとき無効、復元の確認ダイアログで含まれない区分が無効表示、API キーのチェック時に警告が出る、復元の確認ダイアログの内容(件数・日時)、キャンセル(`null`)、完了後に再起動の確認が出る。
- 手動(09 に追加): Windows で、画像を含む取得 → 別フォルダ・別データで復元 → 再起動後にギャラリー・プリセット・会話・設定が戻る。数 GB のバックアップの所要時間とメモリ使用量。取得中の生成。復元中のアプリ強制終了後の状態(§4.3)、別 PC(ComfyUI のパス・画像保存先が存在しない状態)での復元。macOS(同様)。

## 8.5 ユーザー機能との関係(今後の追加予定への配慮)

今後ユーザー機能(ユーザーごとに設定・ギャラリー・プリセットを持つ)が追加される予定。方針は次のとおり。

- **インポートは「ログイン中のユーザーのデータ」に対して行う**(各ユーザーでログインしたあとに取り込む運用)。したがって、ほかのユーザーのデータには影響しない。
- バックアップの 3 区分(設定値・ギャラリー・プリセット)は、**ユーザーごとのデータ区分とそのまま対応**させる。今回はユーザーが存在しないので、全体が 1 ユーザー分(= 現在の単一データ)として扱う。`manifest.json` に **ユーザー ID は持たせない**(別ユーザー・別 PC へ取り込めるようにするため)。
- 端末依存の設定(§2。ComfyUI のパス・画像保存先 等)は、今回はバックアップに含めて復元する(Q-214)。**ユーザー機能の導入時に、これらがユーザーのデータか端末のデータか(別ユーザーの取り込みで上書きしてよいか)を再検討する**(07 Q-226)。
- 実装では、復元・取得が「対象テーブルの全行」を直接操作せず、**1 か所の抽象(例: 区分ごとの `BackupScope`: 対象テーブルと除外キー、ファイルの対象を返す)を経由する**。ユーザー導入時に、その抽象へ `user_id` による絞り込みを足せば済むようにするため。今回は `user_id` を扱うコード・列は **作らない**(推測による先行実装はしない)。
- ユーザー機能自体の設計(認証・データ分離・マイグレーション)は **別設計**。導入時にこの資料を更新する(07 Q-226)。

## 11. リスク

- **復元でデータを失う(事前バックアップなし。Q-219)** → 復元は元に戻せない。UI で明示し、確認ダイアログの文言で「先にバックアップを取る」ことを促す。検査(`integrity_check`)を入れ替えの前に行い、途中の失敗は一時退避した DB で巻き戻す(テスト 7〜9)。**成功した復元の取り消しは、利用者が事前に取ったバックアップに頼る**。
- **別 PC でパスが合わない(Q-214)** → ComfyUI が起動できない・保存先が無い状態は設定画面で分かり、手動で直せる。画像保存先は復元時に作成する。設定値のみ復元でギャラリーを残す場合は警告する。
- **孤立画像の削除の誤操作** → 既定 OFF・件数と容量を確認・ゴミ箱へ移す(完全削除しない)。
- **Windows で DB が開いたまま置き換えられない** → ファイルを差し替えず、稼働中の接続に `ATTACH` してトランザクションで置き換える(§4.3)。
- **巨大なバックアップ(数十 GB)の所要時間・容量** → ストリーム処理・進捗・キャンセル・空き容量の事前確認。ギャラリーを外せば画像を含めずに済む。サムネイルを含めるぶん容量は増える(原寸に対して小さい)。
- **API キーの漏洩** → 既定で除外・明示のチェック+警告・ログに出さない(02 §3.8)。含めたバックアップの取り扱いは利用者の責任と UI に明記。
- **悪意のある ZIP(Zip Slip・ZIP 爆弾)** → パスの正規化と拒否・展開サイズの上限(テスト 6)。
- **スキーマの新旧** → 新しいバックアップは拒否、古いバックアップはマイグレーションで上げる。バックアップ形式(`format`)を持ち、将来の変更に備える。

## 12. 受け入れ基準

- 設定 > その他から、設定値・ギャラリー・プリセットをトグル(既定すべて ON)で選んでバックアップを `.gazooo-backup` として保存でき、完了が通知される。取得中も UI・生成をブロックしない。
- 別のデータ状態(例: 新規インストール)から復元すると、含まれていた区分(設定・AI サポートの会話・ジョブの設定・ギャラリー・参照画像・プリセット)が元どおりに戻る。復元する区分は選べ、選ばなかった区分は変わらない。ComfyUI のパス・画像保存先などの端末依存の設定も、バックアップの値で復元される(存在しないパスでも)。
- API キーは既定ではバックアップに含まれない。
- 壊れた・新しすぎるバックアップは、何も変更せずエラーになる。復元の途中で失敗しても、元の状態に戻る。
- 復元は元に戻せないことが UI に明示される(復元前の自動バックアップは取らない)。
- 復元時に「バックアップに無い画像ファイルを削除する」を選べる(既定 OFF。ゴミ箱へ移す)。

## 14. 実装時の判断(設計との差異)

- **DB の入れ替えは `ATTACH` + 1 トランザクション**(§4.3)。当初案の「`gazooo.db` を差し替え + 一時退避」は、Windows で稼働中の接続が掴んでいる間はできず、接続の再構築が必要だった。トランザクションならロールバックで巻き戻せ、退避ファイルも要らない。
- **画像はステージングを経由せず、追加のみで直接展開**する(容量の二重消費を避ける)。DB のステージング(検査用の展開)は `backup_inspect` で行い、`restore-staging/` に置く。
- **空き容量の事前チェックは行わない**(依存の追加が必要)。書き込み失敗(`StorageFull`)で `BACKUP_NO_SPACE` を返す。
- **`BACKUP_BUSY` はジョブのみ**(DB と画像を書くのはジョブだけ。ダウンロード・インストール・LLM は復元の対象を触らない)。
- **スナップショットは `VACUUM` し直す**: OFF の区分や API キーを削除したあと `VACUUM` して、削除した内容が空きページに残らないようにする。
- **`inputs/` の同梱**: 区分ごとの参照を追わず、ギャラリーが ON のとき `inputs/` を丸ごと入れる(プリセットの参照画像も含まれる)。
- **復元したジョブの扱い**: ギャラリーを復元するとき、バックアップ時点で待機中・実行中だったジョブは **取り消し済み(`cancelled`)にして取り込む**。再起動後に勝手に生成が始まらないようにするため(§4.3 の手順 3-2)。
- **復元前のジョブ停止はコマンド層**(`backup_restore` の `stopJobs`)で行い、サービス側は「待機中・実行中のジョブが残っていれば `BACKUP_BUSY`」で最終確認する。フロントは、確認ダイアログの注意書きに同意した復元では常に `stopJobs: true` を送る。
- **`backup_inspect` が DB を `restore-staging/` に展開する**(復元の対象として検査済みのファイルを Rust 側が保持)。孤立ファイルの見込み(`backup_orphans`)は、この展開済み DB を `ATTACH` して数える。復元が成功したときにステージングを削除する(検査だけで復元しなかったときは次の検査で上書き)。
- **孤立ファイルの対象**は、想定のレイアウト(`YYYY/MM/*`・`thumbs/*`・`inputs/*` の `png|jpg|jpeg|webp`)に限る。それ以外のファイル(利用者が置いたもの)は触らない。`inputs/` の参照は、ジョブ・プリセットの `params_json` から `inputs/<ファイル名>` の文字列を拾って判定する(保守的に残す側へ倒す)。
- **`Written.images`** は ZIP に書いたファイル数(原寸 + サムネイル + 参照画像)。UI の「N 件」はこの数。

## 追記(v0.53): 全体設定との関係(52 §6)

バックアップの「設定値」はユーザーの値(個別設定と個人の項目)だけで、全体設定は含まない。復元した個別の画像保存先が、ほかのユーザーの場所・全体の保存先と重なる場合や、以前の版の固定の場所の場合は、その項目だけを戻さず全体設定を使う。
