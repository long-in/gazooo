# 16. アニメ特化モデルの対応(v0.8)

> ステータス: 🟢 承認済み(2026-11-19。Q-57〜67 は推奨どおり)。

## 1. 目的とスコープ

アニメ・イラスト特化のチェックポイントを、アプリで **選びやすく・取得しやすく・使いこなしやすく** する(F-17)。

**現状の整理**: アニメ特化モデルの多く(Animagine XL、Illustrious 系、NoobAI-XL など)は **SDXL 派生** で、通常のチェックポイントとして `checkpoints/` に置けば、既存の `sdxl` 種別でそのまま生成できる(ワークフローの変更は不要)。SD1.5 系のアニメモデルも同様に `sd15` で動く。
つまり不足しているのは **(a) 取得手段、(b) アニメ向けの既定値・書き方の案内** であり、エンジン層(`workflow.rs`)は変更しない。

**やること**
1. モデル取得カタログ(12)に、アニメ特化チェックポイントのファミリーを追加する(§3)。
2. 取得ページ(`/models`)に、用途のフィルタ「アニメ・イラスト」を追加する(§4)。
3. アニメモデル向けの **推奨設定の案内**(プロンプトの書き方・解像度・CFG・サンプラー)を、生成画面の「プリセット」として提供する(§5)。
4. AI サポート(11)の機能カタログに、アニメ系の案内に必要な情報を追加する(§6)。

**やらないこと**
- 新しいモデル種別(`ModelKind`)の追加。**`sd15` / `sdxl` のまま**(§2)。
- Civitai・gated モデルの取得(12 の Q-33 のまま。Pony Diffusion 系は主に Civitai 配布のため、カタログに入らない。§3 注)。
- LoRA の取得・適用(別件)。
- モデルの自動判別(ファイル名・中身からの「アニメ系か」の推定)。

## 2. 種別の扱い(新種別を作らない理由)

- 生成に必要なノード構成(`CheckpointLoaderSimple` → `KSampler` → `VAEDecode`)は、アニメ系でも通常の SDXL / SD1.5 と同一。
- 追加が必要になりうる **Clip Skip**(SD1.5 系アニメモデルで `-2` が慣習)は、**v0.8 では対象外**(§8 Q-59)。SDXL 系アニメモデルでは通常不要。
- したがって `ModelKind`・IPC・DB スキーマ・マイグレーションは **変更なし**。顔補正・ControlNet・Inpaint も、`sdxl` / `sd15` のため **そのまま併用できる**(ControlNet はベースモデル一致が必要 = 10 §3 のまま)。

## 3. 取得カタログへの追加(12 §4.1 のスキーマを拡張)

### 3.1 スキーマの追加フィールド

`ModelFamily` に任意フィールド `tags?: ("anime" | "nsfw")[]` を追加する(用途フィルタ用。将来の拡張に備え配列)。`schemaVersion` は 1 のまま(任意フィールドの追加のため後方互換)。`ModelVariant` の変更はなし。

### 3.2 追加候補(案)

**いずれも、実装時に取得元の「公開状態(gated でない)・ライセンス・SHA-256・コミット固定 URL」を実機で確認し、確認できないものはカタログに入れない**(12 §4.1 の規則)。以下は起案時点の候補であり、確定値ではない。

| ファミリー | ベース | 配布元(候補) | 備考 |
|---|---|---|---|
| Animagine XL 4.0 | SDXL | cagliostrolab/animagine-xl-4.0 | Danbooru タグで指示。ライセンスは Fair AI Public License 系の可能性があり、**同意ダイアログ対象になりうる**(要確認) |
| NoobAI-XL | SDXL | Laxhar/noobai-XL(最新の安定版を実装時に選ぶ) | Illustrious 系の派生。Danbooru / e621 タグ。ライセンス要確認 |
| Illustrious-XL | SDXL | OnomaAIResearch/Illustrious-XL(版は実装時に確認) | **版によって gated の可能性があり、gated なら入れない**(Q-33) |
| SD1.5 系アニメモデル | SD1.5 | (候補を実装時に調査。Hugging Face で認証不要・ライセンスが明確なもののみ) | 無ければ SD1.5 側は追加しない |

- 注: **Pony Diffusion V6 XL** は主な配布が Civitai(許可リスト外、Q-33)のため **対象外**。ユーザーが手動で `checkpoints/` に置いた場合は、通常の SDXL として使える。
- SDXL のチェックポイントはどれも **約 6.5〜7GB** で、容量の目安を variant に表示する(12 のまま)。VAE は各モデルに内蔵のものを使う(別途の取得は不要)。
- 精度違い(fp16 / fp32)が配布されている場合は、**fp16 を推奨** とし、variant として並べる。

### 3.3 NSFW 対応(2026-11-19 追加指示。**2026-11-24 に 18 §10 で置き換え: `nsfw` タグ・「NSFW 対応」フィルタ・表記は廃止し、「規制の強さ」の表示に変更**)

ユーザー指示: 「NSFW に対応した他のモデルも選んでほしい」。

**方針**
- アプリに **生成内容のフィルタは設けない**(ローカル動作のため。ComfyUI 側にもセーフティチェッカーはない)。NSFW に対応するかどうかは **モデルの学習内容** で決まるので、対応するモデルをカタログに載せて選べるようにする。
- 該当するモデルは、ファミリーの `tags` に `"nsfw"` を付ける(§3.1 の `tags` を `("anime" | "nsfw")[]` に拡張)。`/models` の用途フィルタに「NSFW 対応」を追加し、**既定では絞り込まない**(表示は他のモデルと同じ。サムネイルや画像は載せない)。
- 各モデルのライセンスの **利用制限は variant の `license` / 同意ダイアログで必ず表示** する(OpenRAIL 系は利用制限つき)。実在の人物の無断利用、未成年を性的に描くこと、違法な利用は、モデル・アプリのいずれでも認めない旨を、NSFW 対応モデルの同意ダイアログに明記する(ユーザーの責任で適法に利用すること)。

**調べた候補(2026-11-19、Hugging Face の公式ページ)**

| モデル | ベース | ライセンス | NSFW | 認証 | 判断 |
|---|---|---|---|---|---|
| [Animagine XL 4.0](https://huggingface.co/cagliostrolab/animagine-xl-4.0) | SDXL | CreativeML Open RAIL++-M(SDXL 本体と同じ) | レーティング用のタグがあり、対応する(配布元の記載で要確認) | 公式リポジトリに gated の表示は見当たらない | **採用候補**(同意あり) |
| [NoobAI-XL](https://huggingface.co/Laxhar/noobai-XL-1.0) | SDXL(Illustrious-XL 派生) | Fair-AI-Public-License-1.0-SD。Illustrious 側の条件を継承し、派生モデルの公開などの追加条件あり | Danbooru 全量と e621(成人向けも含む画像掲示板)で学習。対応する | 見当たらない | **採用候補**(同意あり。ライセンス文を表示) |
| Illustrious-XL | SDXL | 本調査では確認できず(NoobAI の README が継承元として参照) | 対応(NoobAI の元) | **未確認**。gated なら入れない | 実装時に確認、確認できなければ外す |
| [Chroma1-HD](https://huggingface.co/lodestones/Chroma1-HD) | Flux.1 schnell 派生(8.9B) | Apache-2.0 | 「検閲なし」を掲げる(配布元の表現) | 見当たらない | **今回は見送り**(下記) |

- 「NSFW 対応」の根拠は、配布元の説明と学習データの記載による。**カタログに載せる前に、実装時に各リポジトリの README を読んで確認する**。確認できないものには `nsfw` を付けない。
- **Chroma は見送り**: Flux 派生だが、ComfyUI で使うには専用の読み込み(`diffusion_models`)・T5 のみのテキストエンコーダ・専用のワークフローが要る可能性があり、既存の `flux` / `flux_gguf`(02 §3.4)では動かない見込み。GGUF も第三者の再配布で、公式の取得元(Q-33 の「認証不要・固定ハッシュ」)の要件を別途確認する必要がある。**新しい `ModelKind` を伴う別件の設計** として切り出す(Q-64)。
- Pony Diffusion 系・実写系の NSFW モデルは、主な配布が Civitai のため引き続き対象外(Q-58)。手動で `checkpoints/` に置けば SDXL / SD1.5 として使える。

### 3.4 記事に基づく選定(2026-11-19 追加指示)

参考: [ローカル環境でのおすすめのアニメ系画像生成AIモデル(note・robai104)](https://note.com/robai104/n/n84933ee7beed)。ユーザー追記: **個人利用で商用利用はしない**ため、ライセンスの商用可否は選定の条件にしない(§3.3 の「商用」に関する記述は判断材料から外す。同意ダイアログの文言は、取得元のライセンス名・リンクの表示のみとする)。

記事の推奨(筆者の好みの順は Qwen-Image 2.1 > MiniMax H3 > Krea 2 > Anima > その他)を、**アプリでの扱い方** で分類した。記事の内容は未検証の部分が多く(ベースモデル・サイズ・VRAM の記載がない)、実装前に各取得元で確認する。

| 区分 | モデル | 取得元 | アプリでの扱い |
|---|---|---|---|
| **A. 既存の種別で動く** | SDXL(Illustrious 系): Rouwei 系・Nlxl・illumiyumeXL・Noob(chenkin)系 | **Civitai** がほとんど | ワークフローは `sdxl` のまま。ただし **v-pred 版**(illumiyumeXL、NoobAI の v-pred 版)は `ModelSamplingDiscrete(v_prediction)` が要り、**Noob RF 版**(Rectified Flow)は通常の SDXL と別のサンプリングが要る。`sdxl` の生成パラメータに「サンプリング方式(`eps` / `v_pred` / `rf`)」を追加する設計が必要(03 の `params_json` の拡張のみ・マイグレーション不要) |
| **A'. 同上(Hugging Face)** | NoobAI-XL / Animagine XL 4.0(§3.3) | Hugging Face | そのまま取得できる(先に決めた範囲) |
| **B. 新しい種別が必要** | **Anima**(NVIDIA Cosmos ベースのアニメ特化。記事は「現状ローカルでアニメ調を出すなら最有力」。preview 版は高解像度に弱い) | Hugging Face([circlestone-labs/Anima](https://huggingface.co/circlestone-labs/Anima)) | **最優先の新種別**(`anima`)。Hugging Face にあるので、取得ページの範囲(Q-58)に収まる |
| B | **Qwen-Image 2.1**(NSFW も出せる。参照画像からの生成・日本語に強い。記事の筆頭) | 記事に取得元の記載なし(要調査) | 新種別。参照画像の入力(画像編集)を使う場合は UI も別設計 |
| B | **Krea 2** | Hugging Face(krea/Krea-2-Raw、Turbo) | 新種別。素の画質が良いとされる |
| B | **MiniMax H3**(動画用だが画像も強い。派生は Civitai) | Hugging Face(INT4 変換版など)/ Civitai | 新種別。取得元・形式(量子化)が複雑 |
| B | **Flux.2 Klein 9B** | Civitai | 新種別。記事では NSFW は Illustrious / Anima より弱い |
| B | NewBie image | Civitai | 発展途上と記載されており見送り |

**所見(推奨)**
- 記事の推奨モデルの **大半は Civitai 配布** で、現在の取得ページ(Hugging Face のみ。Q-33・Q-58)では取得できない。記事の選定を活かすには、**Civitai 対応(取得元の拡張)を別設計として検討する必要** がある(許可リストの追加、API キーの保管、ファイル名・ハッシュの扱い)。それまでは、ユーザーが `checkpoints/` に手動で置けば `sdxl` として使える(v-pred / RF はサンプリング方式の追加が必要)。
- **Hugging Face だけで進めるなら**: Animagine XL 4.0・NoobAI-XL(§3.3)に加えて、**Anima(新種別)** を最優先にするのが、記事とも整合する。
- Qwen-Image 2.1・Krea 2・MiniMax H3・Flux.2 Klein は、いずれも **新種別の追加** を伴うため、17 として **1 つの「新モデル種別」設計** にまとめる(種別ごとにワークフロー・必要ファイル(本体 / テキストエンコーダ / VAE)・ComfyUI のノードを調べて定義する)ことを提案する。

## 4. UI

- **`/models`(12 §5)**: カテゴリ「チェックポイント」に、用途フィルタ(すべて / アニメ・イラスト)を追加する。ベースモデルのフィルタ(すべて / SD1.5 / SDXL)と併用できる。
- **生成画面のモデル選択**: 導入済みチェックポイントの一覧は **従来どおりファイル名のまま**(自動判別しない)。取得ページ経由で導入した分は、カタログの名前を併記しない(一覧の仕様を変えない)。
- 生成画面で「アニメ向けの設定にする」ボタンは作らず、§5 のプリセットで対応する。

## 5. アニメ向けプリセット(組み込み)

既存のプリセット機能(F-08)に、**組み込みプリセット** として次を追加する(ユーザーのプリセットとは別に表示。削除・編集は不可、「コピーして使う」は可)。

| プリセット | 内容(案) |
|---|---|
| アニメ(SDXL・縦長) | `kind=sdxl`、832×1216、steps 28、cfg 5.0、sampler `euler_ancestral`、scheduler `normal`。プロンプト欄の先頭に `masterpiece, best quality` などの品質タグを挿入せず、**ネガティブに `lowres, bad anatomy, worst quality` を既定で入れる** |
| アニメ(SDXL・正方形) | 1024×1024、他は上記と同じ |

- 値は **起案時点の目安**。モデルごとに推奨が異なるため(Animagine / NoobAI 等)、実装時に各配布元の推奨を確認して、**共通で無難な値** に絞る。モデル固有のタグ(品質タグ・年齢タグなど)の差は、プリセットでは吸収せず、**AI サポート(§6)と、プリセットの説明文(「Danbooru タグで書くと効きやすい」)で案内する**。
- 組み込みプリセットは、アプリのコード(定数)として持つ。DB には入れない(マイグレーション不要)。ユーザーのプリセットの一覧では、組み込みを上に区別して表示する。
- 生成後の結果(`params_json`)には、他の生成と同様、実際に使った値が保存される(プリセット名は保存しない)。

## 6. AI サポートへの反映(11・13 §6 の機能カタログ)

- 機能カタログに、**アニメ向けの知識** を短く追加する: 「アニメ系 SDXL モデルは Danbooru タグ(`1girl, solo, …`)が効く」「モデルごとに品質タグが異なるため、配布元の説明を確認する」「アニメ向けの組み込みプリセットがある」。
- 追加で **送信する情報は増えない**(固定の説明文のみ。13 §6 のプライバシー方針のまま)。
- 「もっとアニメ調にしたい」(11 §3 の例)への回答で、取得ページのアニメ系モデルを案内できるようにする。
