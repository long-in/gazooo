# 36. ユーザー機能(ユーザーごとの作業スペースとロック)(v0.31)

> ステータス: 🟢 承認済み・実装済み(2026-11-22。07 Q-241〜262 は推奨どおり。`argon2` の追加も承認)。Rust 428・Vitest 278・clippy・ESLint・静的エクスポートのビルドまで確認。画面の目視確認・実機・macOS は未実施。差異は §18。03・04・05・25・29・35・09 への追記は反映済み(§12)。

## 1. 目的とスコープ

1 台の PC を複数人で使えるよう、**ユーザーを作成でき、ユーザーごとに独立した作業スペース**を持たせる。

- 設定・生成物(ギャラリー)・プロンプト(ジョブの設定)・プリセット・AI サポートの会話・API キーなど、**ユーザーのデータはすべてユーザーごとに別**。**ほかのユーザーのデータは、アプリ上で閲覧も操作もできない**。
- 起動時に **ユーザーの一覧(YouTube のアカウント選択のような画面)** を表示し、選んで入る。
- ナビ(左ツールバー)の **上部にユーザー名(アバター)を表示** し、その近くから **ユーザーの切り替え** ができる。
- ユーザーごとに **ロック(パスフレーズまたは PIN)** を設定できる。**既定は無効**。設定 > 「その他」タブで有効化・登録する。
- PIN は、ログイン画面で **金庫を開けるような数字キーパッド** で入力する(クリックでも、キーボードの数字キーでも入力できる)。

### 1.1 ロックの限界(重要。UI にも明記する)

このロックは **アプリの画面上でほかのユーザーが閲覧するのを防ぐ**もので、**ファイルの暗号化ではない**。同じ OS アカウントでエクスプローラーなどから `users/<id>/` を開けば、画像やデータベースは読めてしまう(OS 側のアカウント分離・BitLocker / FileVault は別の話)。データの暗号化(SQLCipher・画像の暗号化)は **今回の対象外**(Q-258)。設定のロック欄に「このロックはアプリ内の保護です。ファイルは暗号化されません」と表示する。

### 1.2 対象外(やらないこと)

- 管理者・権限の区別(全ユーザー対等。Q-251)、ユーザー間のデータ共有・コピー。
- データの暗号化(§1.1)、パスワードの復旧メール・セキュリティ質問などの復旧手段(Q-254)。
- アイドル時の自動ロック・画面ロック(切り替えは手動のみ)。
- OS アカウントとの連携・クラウドのアカウント。
- アバター画像のアップロード(頭文字 + 色。Q-249)。

## 2. 用語と全体構成

- **ユーザー**: 名前・色・ロック設定を持つ。作業スペースを 1 つ持つ。
- **作業スペース**: `{app_data_dir}/users/<user_id>/` 以下のデータ一式(DB・既定の画像保存先)。
- **端末の設定(共有)**: ComfyUI・モデル・ローカル LLM など、**1 台の PC に 1 つしかないもの**。全ユーザーで共通(§4)。
- **ログイン中のユーザー**: Rust 側が 1 人だけ保持する(`CurrentUser`)。フロントはユーザー ID をデータ系コマンドに渡さない(§6)。

### 2.1 ディレクトリ構成

```
{app_data_dir}/
  app.db                        # ユーザーの一覧・端末の設定(§3)
  users/
    <user_id>/
      gazooo.db                 # そのユーザーの DB(設定・ジョブ・画像・プリセット・会話)
      images/                   # 既定の画像保存先(2026/11/…、thumbs/、inputs/)
  comfyui/ models/ llm/ logs/   # 端末共通(従来どおり)
```

- **DB はユーザーごとに別ファイル**(Q-241)。テーブルに `user_id` 列を足す方式は採らない。物理的に分かれるため、データの取り違え・クエリの絞り忘れによる漏れが起きず、ユーザー削除はディレクトリの削除で済み、バックアップ(35)もそのまま「1 ユーザー = 1 つの DB」に対応する。
- 各ユーザーの DB には、従来どおり `src-tauri/src/db/migrations/` のマイグレーションを **ログイン時に適用** する(スキーマは既存のまま。03)。`app.db` には別系統のマイグレーションを持つ。
- 画像保存先は **ユーザーごとの設定**(`storage.images_dir`。既存どおり、変更可)。既定は `users/<id>/images`。

## 3. データモデル(`app.db`)

```sql
CREATE TABLE users (
  id             TEXT PRIMARY KEY,           -- UUID v7
  name           TEXT NOT NULL,              -- 表示名(1〜24 文字。大文字小文字を区別せず一意)
  color          TEXT NOT NULL,              -- アバターの色(パレットのキー)
  auth_kind      TEXT NOT NULL DEFAULT 'none' CHECK (auth_kind IN ('none','pin','passphrase')),
  auth_hash      TEXT,                       -- Argon2id の PHC 文字列(auth_kind が none のとき NULL)
  pin_length     INTEGER,                    -- auth_kind = 'pin' のときの桁数(4〜8)
  failed_count   INTEGER NOT NULL DEFAULT 0, -- 連続失敗回数
  locked_until   INTEGER,                    -- この時刻まで試行不可(UTC ミリ秒)
  created_at     INTEGER NOT NULL,
  last_login_at  INTEGER
);
CREATE UNIQUE INDEX idx_users_name ON users(lower(name));

CREATE TABLE device_settings (               -- 端末の設定(settings と同じ形)
  key        TEXT PRIMARY KEY,
  value_json TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

- 作業スペースのパスは **`users/<id>` を `id` から導出**する(DB に絶対パスを持たない。ユーザー名はパスに使わない)。
- ロックは **Argon2id でハッシュ化**して保存(ソルトは PHC 文字列に含む)。平文は保存・ログ出力しない(02 §3.8)。PIN・パスフレーズの検証は Rust 側のみ。
- **ユーザー数の上限は 20**(`USER_LIMIT`。Q-250)。

## 4. どのデータがユーザーごとで、どれが端末共通か

`settings_get` / `settings_update` の API は **変えない**。Rust 側が **キーの分類表(1 か所の定数)** で、ユーザーの DB と `device_settings` に振り分ける(Q-245)。

| 区分 | 内容 |
|---|---|
| **ユーザーごと** | `ui.theme`・`ui.language`・`ui.state`・`generation.default_params`・フォームの下書き・`storage.images_dir`・`assistant.*`(**API キーを含む**)・プロンプト翻訳の設定(34)・`models.consents`、ジョブ・画像・参照画像・サムネイル、プリセット、AI サポートの会話、ギャラリーの表示設定 |
| **端末共通** | `engine.comfyui.url`・`engine.comfyui.managed`(起動管理のパス・引数)・`engine.comfyui.models_dir`・`debug.enabled`・`llm.*`(アイドル停止・生成前解放) |
| **端末共通(キーではないもの)** | ComfyUI 本体・Python・モデルファイル・ローカル LLM のモデルと `llama-server`・ログ・ダウンロードの状態 |

- **端末共通の設定は、どのユーザーでも編集できる**(権限の区別をしない。Q-251)。巨大なモデルや ComfyUI のプロセスを、ユーザーごとに持たないため。
- 画面の設定ページは、**「端末共通」の項目に「この設定はすべてのユーザーに共通です」と表示**する(エンジン・保存先のモデル保存先・デバッグ)。
- `models.consents`(モデル取得の利用許諾への同意)は **ユーザーごと**(同意は個人の行為のため)。

## 5. ユーザーの画面とフロー

### 5.1 ユーザーゲート(起動時・切り替え時)

アプリ起動時、**ユーザーがログインするまでは本体のシェルを出さず、全画面の「ユーザーの選択」画面だけを表示**する(ルートは増やさず、ルートレイアウトのゲート。静的エクスポートのまま)。

```
        gazooo
   だれが使いますか?

  (A)      (B)      (C)     (+)
 たろう   はなこ    ゲスト   ユーザーを追加
  🔒                          
```

- ユーザーは **カード(大きな丸いアバター + 名前)** で並べる。アバターは **名前の頭文字 + 色**(色はパレットから選ぶ)。ロック有りのユーザーは 🔒 を付ける。並び順は **最後に使った順**(Q-246)。
- カードを選ぶ → ロックなし: そのままログイン / ロックあり: §5.3 の入力へ。
- 末尾の **[+ ユーザーを追加]**: 名前と色を入力して作成 → そのユーザーでログイン(ロックは作成時には設定しない)。
- 各カードの右上(ホバー時)に **「…」メニュー**(名前の変更・削除)。名前の変更・削除は §5.5。
- **ユーザーが 1 人だけでロックなしの場合も、一覧を出す**(指示どおり。1 クリックで入れる。Q-247)。
- Esc・戻るボタンでの抜け方はない(ユーザーを選ぶまで本体に入れない)。

### 5.2 ナビ上部のユーザー表示と切り替え

- 左ツールバー(48px。29)の **最上部** に、現在のユーザーの **アバター(頭文字 + 色)** を置く。ホバーのツールチップに **ユーザー名**。
- **クリックでポップオーバー**を開く:
  - ユーザー名(大きく)・[ユーザーを切り替える]。
  - [設定のロック…](設定 > その他 > ロックへ移動)。
- ツールバーが狭くて名前が見えないため、**ポップオーバーの見出しに名前を出す**。名前を常時表示したい場合に備え、**ツールバーを開いたとき(幅が広い密度の設定)は名前も並べて表示**する(29 §6 の `ui.state` の密度に従う。Q-248)。
- [ユーザーを切り替える] → §5.4。

### 5.3 ロックの入力

**パスフレーズ**: 1 つのパスワード入力欄(表示/非表示の切り替え付き)+ [ログイン]。Enter で送信。

**PIN(金庫のキーパッド)**: ユーザー選択後に表示する。

```
        たろう
   ● ● ○ ○          ← 桁数ぶんのドット(入力済みが塗りつぶし)

   [1] [2] [3]
   [4] [5] [6]
   [7] [8] [9]
   [⌫] [0] [↵]
        [戻る]
```

- **クリック**でも、**キーボードの数字キー(0〜9、テンキー含む)** でも入力できる。`Backspace` で 1 桁削除、`Esc` で全消去、`Enter` で送信。入力したキーに合わせて画面のキーが押し込まれる表示にする。
- **桁数に達したら自動で送信**する(桁数は PIN 登録時に 4〜8 から選ぶ。`users.pin_length`。Q-255)。
- 間違えたときは **ドットが左右に揺れて(金庫が開かない動き)全消去**。残り回数・待ち時間を表示(§7)。
- 「戻る」でユーザー選択へ。
- 視覚効果は控えめ(`prefers-reduced-motion` のときは揺れを出さず、文言で知らせる)。

### 5.4 切り替え

1. [ユーザーを切り替える] を押す。
2. **実行中のジョブがあれば確認**: 「生成中のジョブがあります。取り消して切り替えますか?」[取り消して切り替える] [戻る]。待機中のジョブは **そのユーザーの DB に残り、次にそのユーザーでログインするまで実行されない**(Q-252)。バックアップの復元・ダウンロード中などは、切り替えを妨げない(端末共通の処理のため)。
3. Rust 側で `CurrentUser` を解除(そのユーザーの DB 接続を閉じ、アセットのスコープから作業スペースを外す)。
4. フロントは **ウィンドウをリロード**して、メモリ上の状態(ストア・キャッシュ・ギャラリーのサムネイルなど)を **すべて破棄**し、ユーザーゲート(§5.1)を出す(Q-253。前のユーザーのデータが画面に残らないことを保証する最も確実な方法)。

### 5.5 名前の変更・削除

- **名前の変更**: ロックありのユーザーは、そのユーザーのロックの入力が必要(ログイン中の自分自身は不要)。
- **削除**: **そのユーザーのデータをすべて削除する(元に戻せない)**ことを確認する。作業スペース `users/<id>/` をゴミ箱へ移さず **完全削除**する(Q-256。サムネイル・画像が大量で、ゴミ箱に残ると「閲覧できない」要件に反するため)。
  - ロックありのユーザーを削除するには、**そのユーザーのロックの入力が必要**。
  - **ロックを忘れたとき**: 削除の確認ダイアログに [ロックを忘れた場合] を置き、**「このユーザーのデータをすべて削除して作り直す」**に進める(復旧手段はない。Q-254)。ロックはファイルを暗号化していないため、これは「他人のデータを見る」手段にはならないが、データは失われる。強い警告と、ユーザー名の入力による確認を要求する。
  - **ログイン中のユーザー自身は削除できない**(切り替えてから)。**最後の 1 人は削除できない**(`USER_LAST`)。
  - ジョブが実行中・待機中のユーザーでも削除できる(待機中のジョブも消える)。ただし、**今ログイン中のユーザーのジョブが実行中**のときは、削除対象でない限り影響しない(削除はそのユーザーがログアウト中にしか実行できないため、実行中ジョブは常に対象外)。

## 6. 権限の境界(データの分離)

フロントからは **ユーザー ID でデータを指定させない**。分離は Rust 側で強制する。

- `AppState` に `current_user: RwLock<Option<UserSession>>`(`UserSession` = ユーザー ID・DB 接続・作業スペースのパス)を持つ。**データ系コマンドは、すべて `CurrentUser` 経由でのみ DB と画像保存先を得る**。未ログインでは `NOT_LOGGED_IN`(例外はユーザー系コマンドと端末共通の設定・エンジン状態の読み取り)。
- **アセットプロトコルのスコープ**(WebView が画像を読む許可。現在は起動時に画像保存先を許可している)は、**ログインしたユーザーの画像保存先だけ**を許可し、ログアウト時に外す。ほかのユーザーの画像を `asset:` で読めない。
- **ジョブキュー・ワーカーは `UserSession` に属する**(ログイン時に開始、ログアウト時に停止)。ユーザー A の待機中ジョブは、B がログインしている間は実行されない(Q-252)。
- ComfyUI・ローカル LLM は端末共通のプロセスで、ユーザー切り替えをまたいで動き続けてよい(LLM は生成前解放・アイドル停止の既存挙動)。**ただし、ログアウト時に実行中の LLM 呼び出し・翻訳・AI サポートのストリームは中止**する。
- `dialog` 経由のファイル選択・エクスポートは、従来どおり Rust 側で行う(31・35 と同じ)。
- **既知の残余リスク(Q-259)**: ComfyUI 自体の `input/`・`output/`・`temp/` フォルダ(端末共通)には、参照画像のコピーや生成物の一時ファイルが残りうる。アプリの画面からは見えないが、ファイルとしては残る(§1.1 と同じ理由)。アプリは生成物を作業スペースへ取り込んだあと、ComfyUI 側の一時ファイルの削除を **既存の挙動のまま**とし、今回は追加しない。

## 7. ロックの仕様

### 7.1 設定(設定 > その他 > 「ロック」セクション)

ログイン中のユーザー自身のロックを設定する。[保存] ボタンの対象外(31・35 と同じ。即時反映)。

```
ロック
┌──────────────────────────────────────────────────────┐
│ [ ○─ ] このユーザーをロックする(既定: 無効)              │
│                                                      │
│ 方式:  (●) PIN(4〜8 桁の数字)   ( ) パスフレーズ      │
│ PIN の桁数: [4 ▾]                                     │
│ 新しい PIN:        [ ● ● ● ● ]                        │
│ もう一度:          [ ● ● ● ● ]     [登録]              │
│                                                      │
│ ⓘ このロックはアプリ内の保護です。ファイルは暗号化されません。  │
│ ⓘ 忘れた場合、復旧はできません(ユーザーを削除して作り直し)。  │
└──────────────────────────────────────────────────────┘
```

- **既定は無効**(`auth_kind = 'none'`)。トグルを ON にして、方式と値を登録するまで有効にならない(登録前に ON のまま残さない)。
- **方式の変更・ロックの解除・値の変更は、現在のロックの入力を要求する**。ログイン済みでも要求する(席を離れたすきに設定を変えられないように)。
- **PIN**: 4〜8 桁の数字。桁数を選んでから入力(自動送信のため。§5.3)。確認入力が一致しないと登録できない。「0000」「1234」のような単純な PIN は **警告のみ**(登録は妨げない)。
- **パスフレーズ**: **8 文字以上**(上限 128)。確認入力が一致しないと登録できない。強度の表示は出さない(文字数のみ)。
- PIN とパスフレーズの併用はしない(ユーザーごとにどちらか 1 つ。方式を変えるときは付け替え)。

### 7.2 ログイン

- 検証は Rust 側の `user_login`(Argon2id)。成功で `failed_count = 0`・`last_login_at` を更新。
- **総当たりの対策**(特に 4 桁の PIN は鍵空間が小さいため。Q-257): 連続 5 回失敗で **30 秒の待機**、以降 **失敗のたびに 2 倍**(最大 15 分)。`failed_count` と `locked_until` は **`app.db` に保存**し、アプリを再起動しても消えない。待機中は `AUTH_LOCKED_OUT { retryAfterMs }` を返し、UI にカウントダウンを表示する(キーパッドは無効化)。
- 成功時のみ待機をリセットする。ユーザーを選び直しても待機は残る。
- エラーメッセージは「PIN が違います」のみ(桁・内容の手がかりを出さない)。

### 7.3 ロックと他の機能

- **バックアップ(35)**: 取得・復元は **ログイン中のユーザーのデータに対して** 行う(35 §8.5 の方針どおり)。**ユーザーのロックのハッシュ(`app.db`)はバックアップに含めない**(別ユーザー・別 PC へ取り込んだとき、ロックが上書きされないように)。端末共通の設定(§4)は、バックアップの「設定値」に **含めない**(35 §2 の「端末依存の設定」は、本機能で `device_settings` に移るため対象から外れる。Q-226 の再検討結果。Q-260)。
- **デバッグログ(31)**: ログにユーザー名・PIN・パスフレーズを出さない。ユーザー ID(UUID)は出してよい。

## 8. 既存データの移行(初回起動時)

ユーザー機能が入る前から使っている人のデータを、**最初のユーザー** に引き継ぐ。**ファイルは移動しない**(画像は数 GB になりうる。失敗時のリスクを避ける)。

1. 起動時に `app.db` が無く、従来の `gazooo.db` がある → 移行を実行。
2. `app.db` を作成し、最初のユーザーを 1 人作る(名前は **「ユーザー 1」**(en: "User 1")、色は既定。ロックなし。あとから名前を変更できる)。
3. `users/<id>/` を作り、`gazooo.db`(と `-wal` / `-shm`)を **コピー**して検証する(`PRAGMA integrity_check`)。成功したら、旧 `gazooo.db` を **`gazooo.db.pre-users`** にリネームして残す(自動では削除しない。03 の `.bak` と同じ考え方)。
4. **画像は移さない**: 最初のユーザーの `storage.images_dir` を、**従来の実効値**(未設定なら `{app_data}/images`)の絶対パスで明示的に設定する。新しいユーザーは `users/<id>/images`。
5. 端末共通のキー(§4)を、コピーした DB の `settings` から `device_settings` へ **移して**(コピー後に元の DB からは削除)、以降は `device_settings` が正とする。
6. 途中で失敗したら、作りかけの `app.db` と `users/` を削除して従来の状態に戻す(旧 `gazooo.db` は 3 の最後まで変更しない)。アプリはエラー画面で「詳細はログ。再起動で再試行できます」と案内し、ユーザーゲートには進まない。

- 移行は **一度きり**(`app.db` が存在すれば実行しない)。新規インストールは、ユーザーが 0 人の状態で起動し、**最初に「ユーザーを作成」画面**を出す(§5.1 で 1 人目を作る)。

## 9. エラー(04 のエラーコードに追加)

| code | 意味 | 表示 |
|---|---|---|
| `NOT_LOGGED_IN` | ログインしていない状態でデータ系コマンドを呼んだ | ユーザーゲートへ戻す(通常は発生しない) |
| `AUTH_FAILED` | PIN・パスフレーズが違う | キーパッドの揺れ + 文言 |
| `AUTH_LOCKED_OUT` | 失敗回数で待機中(`retryAfterMs`) | カウントダウン |
| `USER_NAME_TAKEN` | 同名のユーザーがいる(大文字小文字を区別しない) | 入力欄のエラー |
| `USER_LIMIT` | ユーザー数が上限(20) | ダイアログ |
| `USER_LAST` | 最後の 1 人は削除できない | ダイアログ |
| `USER_BUSY` | ジョブ実行中のままの切り替え・削除などで確認が必要 | 確認ダイアログ(§5.4) |
| `VALIDATION` | 名前・PIN・パスフレーズの形式が不正(既存) | 入力欄のエラー |

## 10. IPC(04 に追記する内容)

ユーザー系コマンドは **未ログインでも呼べる**(一覧・作成・ログイン)。

| コマンド | 入力 | 出力 |
|---|---|---|
| `user_list` | – | `UserSummary[]`(`{ id, name, color, authKind: "none"\|"pin"\|"passphrase", pinLength: number\|null, lockedUntil: number\|null, lastLoginAt: number\|null }`。**ハッシュは返さない**。最後に使った順) |
| `user_create` | `{ name: string; color: string }` | `UserSummary`(作成後に **自動ログインはしない**。フロントが続けて `user_login`) |
| `user_login` | `{ id: string; secret?: string }`(ロックなしは `secret` 不要) | `{ user: UserSummary }`(失敗は `AUTH_FAILED` / `AUTH_LOCKED_OUT`) |
| `user_logout` | `{ cancelJobs?: boolean }`(実行中ジョブがあり `cancelJobs` が false なら `USER_BUSY`) | `void`(完了後、フロントがリロード) |
| `user_current` | – | `UserSummary \| null` |
| `user_rename` | `{ id: string; name: string; secret?: string }`(自分以外のロック有りは `secret` 必須) | `UserSummary` |
| `user_delete` | `{ id: string; secret?: string; confirmName?: string }`(ロック有りは `secret`。「ロックを忘れた」は `secret` なしで `confirmName` = ユーザー名が一致) | `void`(自分自身は `VALIDATION`、最後の 1 人は `USER_LAST`) |
| `user_lock_set` | `{ kind: "pin"\|"passphrase"; secret: string; pinLength?: number; current?: string }`(ロック有りの現在値は `current` 必須) | `UserSummary` |
| `user_lock_clear` | `{ current: string }` | `UserSummary` |

- 型は Rust 側の定義と一致させる(`src/lib/tauri/user.ts` の薄いラッパー)。
- **`secret` はログ・エラー・イベントに出さない**。メモリ上で使い終わったら上書きする(`zeroize` は新規依存のため、まず標準の範囲で行う)。
- 既存の `settings_get` / `settings_update` は、**ログイン中のユーザーの設定と端末共通の設定を、キーの分類表で振り分ける**(§4)。シグネチャは変えない。
- イベント: `user:changed`(ログイン・ログアウト。ほかのウィンドウ用。現状は 1 ウィンドウのため予約のみ)。

## 11. 実装方針(承認後)

- Rust:
  - `services/users/{mod.rs, store.rs, auth.rs, migrate.rs, paths.rs}`、`commands/user.rs`、`db/app_db.rs`(`app.db` とそのマイグレーション)。
  - `AppState` の DB・画像保存先・ジョブキュー・ワーカーなど、**現在グローバルに持っているユーザーデータの参照を `UserSession` 経由に置き換える**(影響範囲が大きい。段階 A で一括して行い、テストで未ログイン時の `NOT_LOGGED_IN` を網羅する)。
  - アセットのスコープをログイン・ログアウトで動的に切り替える(`lib.rs` の起動時の許可を廃止)。
  - **新しい依存**(承認が必要。AGENTS.md §2): `argon2`(Argon2id のハッシュ。`=x.y.z` で固定)。乱数は、既存の依存の範囲(`getrandom` / `rand` の導入状況を確認)で賄い、増える場合は別途承認を得る(Q-243)。
  - パスは `std::path` のみ。Windows の長いパス・大文字小文字(ユーザー名は ID でパスを作るため影響なし)。
- フロント:
  - `components/users/{user-gate.tsx, user-card.tsx, pin-pad.tsx, passphrase-form.tsx, user-menu.tsx}`(shadcn/ui + Tailwind)。ルートレイアウトでゲートを出す。
  - `components/settings/lock-section.tsx`(`other-section.tsx` から呼ぶ)、`src/lib/tauri/user.ts`、`user-store`(ログイン状態)、`user.*` の i18n(ja / en)。
  - PIN パッドはキーボードを `keydown` で受ける(入力欄を持たない。数字・テンキー・Backspace・Enter・Esc。IME の影響を受けない)。スクリーンリーダー向けに `aria-label`(「1」…)とライブ領域(入力桁数・エラー)を付ける。
- 設定・生成ページなどの既存画面は、**ユーザー切り替え時のリロードに頼る**ため、ユーザー単位のキャッシュ破棄の個別実装は不要。

## 13. テスト

- Rust:
  1. **分離**: ユーザー A・B で別々にジョブ・画像・プリセット・会話・設定を作り、一方のデータがもう一方から **一切見えない**(コマンド経由・DB ファイルとも別)。B でログイン中、A の画像のパスがアセットのスコープ外。
  2. 未ログインでデータ系コマンドが `NOT_LOGGED_IN`。ログアウト後も同様。
  3. **設定の振り分け**: 端末共通のキーは全ユーザーに共通、ユーザーごとのキーは別。分類表にないキーはユーザーごとに入る(漏れのない既定)。
  4. **ロック**: 既定は `none`。PIN・パスフレーズの登録・変更・解除(現在値が必須)。誤った値は `AUTH_FAILED`、5 回で `AUTH_LOCKED_OUT`、2 倍の待機、**再起動後も待機が残る**、成功でリセット。ハッシュが `UserSummary` やログに出ない。パスフレーズ 8 文字未満・PIN の桁数違いを `VALIDATION`。
  5. ユーザー名の一意(大文字小文字を区別せず)・上限 20・長さ。
  6. 削除: 作業スペースが完全に消える、自分自身・最後の 1 人は拒否、ロック有りは `secret` 必須、「ロックを忘れた」は `confirmName` 一致のみ。
  7. **移行**: 従来の `gazooo.db` と画像から、最初のユーザーに引き継がれる(設定・ジョブ・画像が読める。画像は移動せず、`storage.images_dir` が旧位置を指す)。端末共通のキーが `device_settings` に移る。途中の失敗で元の状態に戻る。2 回目の起動で再実行されない。
  8. ログアウト時: 実行中ジョブの確認(`USER_BUSY`)・`cancelJobs` での取り消し・待機中ジョブが他ユーザーのログイン中に走らない。LLM・翻訳のストリームが中止される。
  9. バックアップ(35): ログイン中のユーザーのデータだけが対象。`app.db` のロックのハッシュと端末共通の設定が含まれない。
- フロント(Vitest): ユーザーゲートの一覧・追加・ロックのアイコン、PIN パッドの**クリックとキーボード入力**・自動送信・誤入力のリセット・待機のカウントダウン、パスフレーズの入力、ナビ上部のユーザー表示と切り替え、実行中ジョブの確認ダイアログ、設定 > ロックの有効化(既定は OFF・確認入力の不一致・現在値の要求)、切り替え後のリロード。
- 手動(09 に追加): Windows で、複数ユーザーの作成・切り替え・ロック(PIN・パスフレーズ)・削除、再起動後の待機の保持、**従来の単一データからの移行**(画像が表示される)、PIN パッドのキーボード・テンキー入力、`prefers-reduced-motion`、ユーザー切り替え後に前のユーザーの画像・プロンプトが残らないこと、macOS(同様)。

## 15. リスク

- **改修範囲が広い**(DB・ジョブ・画像・アセット・設定のすべてがログイン状態に依存)→ 段階 A に集中させ、未ログイン時の拒否と分離のテスト(§13 の 1〜3)を先に書く。ユーザー切り替えはウィンドウのリロードで状態を確実に破棄する。
- **ロックを暗号化と誤解される** → 設定・ログイン画面に「アプリ内の保護で、ファイルは暗号化されない」と明記(§1.1)。暗号化は将来の別設計(Q-258)。
- **ロックを忘れてデータが取り出せなくなる** → 復旧手段はなく、削除して作り直すのみ(Q-254)。設定画面で登録時に警告。バックアップの取得を勧める文言を添える(35)。
- **4 桁 PIN の総当たり** → 失敗回数に応じた待機(指数。再起動でも保持)。桁数は最大 8 桁まで選べる。ただしファイル直接の読み取りには無力(§1.1)。
- **移行の失敗でデータを失う** → ファイルを移動せずコピー + 検証 → 旧 `gazooo.db` を `.pre-users` に残す(自動削除しない)。
- **端末共通設定を他のユーザーが変えられる** → 権限を設けない方針(Q-251)。誤操作の影響が大きい項目(ComfyUI のパス・モデル保存先)は「全ユーザーに共通」と表示する。
- **ComfyUI の一時ファイルが端末側に残る**(§6 Q-259)→ 既知の限界として明記。
- **Windows のファイルロック**: ユーザー削除時に DB・画像が開いたままだと削除できない → 対象ユーザーはログアウト中(接続を閉じている)のときだけ削除でき、削除前に確認する。失敗したら残りの削除を再試行できる状態を保つ。

## 16. 受け入れ基準

- 起動時にユーザーの一覧が出て、選んで入れる。ユーザーを追加できる。ナビ上部に現在のユーザー名(アバター)が出て、近くのメニューから切り替えられる。
- ユーザーごとに、設定・ギャラリー・プロンプト・プリセット・AI サポートの会話・API キーが完全に別で、**ほかのユーザーのものは画面から見えない**(切り替え後にメモリ上にも残らない)。
- ロックは既定で無効。設定 > その他で、PIN またはパスフレーズを有効化・登録・変更・解除できる(現在値の入力が必要)。
- PIN のユーザーは、ログイン画面で数字キーパッドが出て、クリックでもキーボードの数字キーでも入力できる。誤入力が続くと待機する(再起動でも保持)。
- 従来のデータは、最初のユーザーにそのまま引き継がれる(画像を移動しない)。
- ロックが暗号化ではないこと、忘れたときに復旧できないことが UI に明記される。

## 18. 実装時の判断(設計との差異)

- **`Db` は差し替え可能なハンドル**(`db/mod.rs`)。全サービスが同じハンドルを共有し、ログイン・ログアウトで中身(ユーザーの DB 接続)が入れ替わる。サービスの引数・構成は変えていない。未ログインの `call` は `NOT_LOGGED_IN`。端末共通の設定だけは `call_device`(未ログインでも使える接続)で読み書きする。
- **端末共通の設定の振り分けは、設定の読み書きの 1 か所(`db::settings_table`)**で行う。ユーザーの接続には `app.db` を `app` として `ATTACH` している。
- **asset プロトコルのスコープは、ログアウトで取り消せない**(Tauri に取り消しの API が無い。`forbid` は恒久的で、同じユーザーの再ログインを妨げる)。ログインで画像保存先を許可するのみ。分離は「データ系コマンドがログイン中のユーザーのパスしか返さない」ことで保つ(§6 の「ログアウト時に外す」を変更)。
- **ロックの保存形式**は `argon2id$m=…,t=…,p=…$<ソルト hex>$<ハッシュ hex>`(`argon2` 0.6.0 の低レベル API `hash_password_into` のみ使用。`password-hash` は使わない)。ソルトは UUID v4(OS の乱数)の 16 バイト。
- **ロックの入力なしで `user_login` を呼ぶ**(ロックありのユーザー)のも、失敗として数える。
- **ロックの設定・変更では、入力の形式(桁数・文字数)を先に検証**し、形式の誤りでは失敗回数を増やさない。
- **`user_delete` が作業スペースの外の画像保存先を返す**(§5.5 は作業スペースのみ削除としたが、最初のユーザーは旧位置に保存先が固定されるため。自動では削除せず、トーストで知らせる)。
- **ログイン時の後処理はコマンド層**(`user_login`): 画像保存先の作成と許可、前回の実行中ジョブの復旧、ワーカーの起床、サムネイルの補完。ログアウトの前処理(`user_logout`)は、実行中ジョブの取り消し(確認済みのときのみ)と相談・翻訳の中止。ジョブのワーカーは、ログインするまで待機する。
- **起動時の ComfyUI の自動起動・デバッグログの復元・ComfyUI の URL は、端末共通の設定から**(ログイン前に行う)。
